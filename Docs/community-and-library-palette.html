The AbundanceTable, the five phases & the library palette

One object, five kinds of operation, and — for each — the real library calls underneath, each linked to its docs. This page maps the raw material we build on; the Ask-SLM API is designed on top of it.

1Glossary

The small, stable vocabulary the whole toolkit is written in.

AbundanceTable
The whole object: a thin wrapper over a biom.Table holding the three parts below.
feature
One microbe in the table — an NCBI taxon. This is the one word we use. (biom's axis name is “observation”; “OTU” / “ASV” are synonyms.)
sample
One sequencing run (its accession, acc).
counts
The matrix of read counts — samples against features. self_count = reads assigned directly to a feature.
sample metadata
Attributes of each sample: cluster, day, host. What we filter and split by.
feature metadata
Attributes of each feature: its full NCBI lineage / taxonomy.
lineage
A feature's chain of NCBI ancestors (… → genus → species).
clade
A feature and everything beneath it; selected when a taxid appears in the lineage.
rank
A level of the taxonomy (phylum, genus, species, …).
relative abundance
Counts normalised so each sample sums to 1.
alpha diversity
Diversity within one sample (richness, evenness).
beta diversity
Dissimilarity between samples (Bray-Curtis: 0 identical, 1 nothing shared).
group
One sub-table from a split (a stratum); a study's groups are its cohorts.

2The object: AbundanceTable

A microbial community is one object — a thin wrapper over a biom.Table — made of three aligned parts.

Counts

The matrix — samples against features. Each cell is a read count.

Sample metadata

One row per sample — e.g. cluster, day, host.

Feature metadata

One row per feature — e.g. its full lineage / taxonomy.

Sample metadata describes the rows, feature metadata describes the columns, the counts matrix sits between.

Why one object, but the parts stay separate

“One object” does not mean one merged spreadsheet. A biom.Table — like phyloseq and QIIME 2 — keeps the counts matrix, the feature metadata and the sample metadata as separate, id-aligned slots in one container. biom does the storage and heavy lifting; Ask-SLM only adds names and the few pieces of real logic libraries don't have.

Querying — read the parts back

The attached metadata is queryable with one call per axis; the result is a plain pandas DataFrame you explore with pandas. No custom code needed.

sm = table.metadata_to_dataframe("sample")        # ask: sample metadata as a DataFrame
fm = table.metadata_to_dataframe("observation")   # ask: feature metadata as a DataFrame

keep = sm.index[sm["day"] == 0]                    # answer: the sample ids you want
sub  = table.filter(keep, axis="sample")           # subset — counts AND metadata travel together

Table.metadata_to_dataframe(axis) is the built-in for this.

Counts and metadata move together — for free

Metadata lives on the axis, so a filtered table already carries the subset metadata — nothing to re-sync. filter even accepts the predicate directly, collapsing ask + subset into one call: table.filter(lambda v, i, md: md["day"] == 0, axis="sample").

4ingest  Acquire raw data

Pull raw data out of wherever it lives. Input varies and barely matters; output is the contract — always the same tidy tables: a taxonomy table (acc, tax_id, self_count, total_count, rank, name) and a sample-metadata table (one row per acc).

GoalLibrary callWhat it does · key params
read a delimited reportpandas.read_csv(path, sep, usecols, dtype)parse a Kraken/Bracken/CSV/TSV report. sep = delimiter, usecols = columns to keep, dtype = force tax_id to int.
read a spreadsheetpandas.read_excel(path, sheet_name)parse an .xlsx metadata sheet (e.g. the cluster map).
load an existing biombiom.load_table(path)read a .biom file straight into a Table — already carries counts + both metadata.
fetch from SRAexternal: pysradb / Entrezquery run accessions → run info & profiles. An integration, not one call.
Ask-SLM logicStandardise every source to one schema. pandas reads bytes; it does not know our columns. The Accessor (one per source) renames/selects the columns and coerces tax_id to int — the minimum for downstream libraries to work. It does not defensively validate; we trust the input (see the data contract). A new source is a new Accessor.

5build  Assemble one table

Derive the feature metadata, align the three parts by id, wrap a biom.Table. Counts stay atomic (self_count); no clade or rank baked in.

GoalLibrary callWhat it does · key params

rank of each nodeNCBITaxa.get_rank(taxids)→ {taxid: "species" | "genus" | …}.
name of each nodeNCBITaxa.get_taxid_translator(taxids)→ {taxid: scientific name}.
make the containerbiom.Table(data, observation_ids, sample_ids)construct from a 2-D matrix + the ids for each axis.
attach metadataTable.add_metadata(md, axis)attach {id: {field: value}} dicts to an axis, matched by id.
reshape long→matrixDataFrame.pivot_table(index, columns, values, aggfunc, fill_value)long taxonomy table → features × samples matrix. values="self_count", aggfunc="sum", fill_value=0.
Ask-SLM logiclineage_table — fold the three ete3 dicts into one feature-metadata table keyed by tax_id (lineage + rank + name) and precompute the ancestor-at-each-rank mapping. build — pivot the counts, align all three parts by id, wrap. No defensive validation.

lineage_table(taxids) — the one piece worth building

The only genuinely new logic in this phase. Spec, no implementation yet:

Inputan iterable of NCBI tax_ids — the features present in the counts.
Outputa tidy table, one row per tax_id: its full lineage (ancestor taxids, root→tip), its rank, its name, and the ancestor taxid at each standard rank (so clade-filter and rank-collapse can read it).
Doesbatch-calls ete3 (get_lineage_translator + get_rank + get_taxid_translator) and stitches the three dicts into one frame keyed by tax_id. ete3 translates merged / deprecated ids; an unresolvable id yields an empty lineage and is simply dropped later by the clade filter.
Becomesthe feature metadata attached to the table at build.
Why self_count, not total_count. self_count = reads assigned directly to a feature (atomic, non-overlapping, safe to sum). total_count already includes the whole sub-tree, so summing it double-counts. The rank roll-up re-derives the clade total itself.

6transform  Reshape the table (1 → 1)

Each call takes a table and returns a table, so they chain. biom does the mechanics; the rules we feed in are ours.

GoalLibrary callWhat it does · key params
keep features/samplesTable.filter(ids_to_keep, axis, invert, inplace)ids_to_keep = an iterable of ids or a function f(values, id, md) → bool; keeps where true. axis="observation" for features.
roll up to a rankTable.collapse(f, norm=False, axis="observation")group vectors by f(id, md) → label. norm=False sums; norm=True (default) averages. Atomic counts → per-rank counts.
relative abundanceTable.norm(axis="sample", inplace)divide each sample by its total so it sums to 1.
even sampling depthTable.subsample(n, axis="sample", with_replacement, seed)randomly rarefy each sample to n reads (drops samples below n).
presence / absenceTable.pa(inplace)convert counts to 0/1.
per-vector mathsTable.transform(f, axis, inplace)apply f(values, id, md) to each vector (e.g. log).
compositional transformcomposition.clr(mat) after multi_replace(mat)centre-log-ratio of each composition; multi_replace swaps zeros for tiny values first so the log is defined.
Ask-SLM logicThe predicates and grouping functions passed to filter/collapse: “is this clade's taxid in the lineage?”, “what is this feature's ancestor at rank?”, prevalence / minimum-abundance thresholds, dropping unclassified features. biom executes them; the rules are ours.
Clade by taxid, not rank name. NCBI renamed superkingdom to domain, so label matching is brittle. Testing “taxid 2 ∈ lineage” works at any level.

7split  Partition into groups (1 → N)

Cut one table into many along a sample-metadata column — one full table per distinct value.

GoalLibrary callWhat it does · key params
keep one value's samplesTable.filter(ids_to_keep, axis="sample")the only library primitive here — keep the samples matching one value. No library call returns many tables at once.
Ask-SLM logicsplit is genuinely ours: take a column, find its distinct values, return a dict[value → AbundanceTable] by filtering once per value. The only 1→N operation — disciplined, repeated filtering.

8analyze  Measure & compare — the full palette

The widest phase: take a community (or several groups) and return a measurement. Almost entirely library territory — scikit-bio and scipy are deep here. Bray-Curtis is one cell in family C.

E · Longitudinal — change over time

Question: how does a subject's community move across timepoints?

No single library call. The building block is beta_diversity; everything else is selection over sample metadata.

Ask-SLM logicFor each subject: pick the day-0 sample (within a tolerance) and the last sample, restrict to that pair, take the beta_diversity distance, assemble one row per subject. Variants: distance-from-baseline and volatility. This selection is genuinely ours.

9Data contract — what we assume

Trust the input; fail fast. The user is responsible for supplying well-formed data. We do the work or let the underlying library raise — no validation layers, no friendly error messages, minimum code. The assumptions below are the things we are allowed to take for granted, so that none of them needs a check. If robustness is ever needed (a public API, untrusted uploads), validation is added at one place — the Accessor boundary — and nowhere else.

The taxonomy table (raw counts)

  • Every tax_id is a real NCBI taxid — an integer, non-null, resolvable by ete3.
  • self_count and total_count are non-negative integers, non-null.
  • self_count is atomic — non-overlapping across features within a sample — so summing is valid.
  • acc (the sample id) is a non-empty string on every row.

The sample-metadata table

  • Exactly one row per acc; no duplicates.
  • Every column we filter or split by exists and is already the right type (day numeric, etc.) — no coercion, no whitespace/case cleanup.
  • Categorical values are spelled consistently (one cluster = one spelling).

The counts matrix at build time

  • Raw integer reads, not pre-normalised.
  • Every sample has > 0 total reads, so norm never divides by zero; no empty samples.
  • Feature ids align between the counts and the feature metadata.

Taxonomy / ete3

  • The ete3 NCBI database is built and present locally (offline) at ~/.etetoolkit/taxa.sqlite.
  • A tax_id ete3 cannot resolve yields an empty lineage → that feature is silently dropped by the clade filter. Acceptable, not an error.

Analysis time

  • A grouping column passed to PERMANOVA / ANCOM / etc. defines a valid comparison (≥ 2 groups, enough samples). If not, the library raises — we do not pre-check.
  • Longitudinal: a subject lacking a baseline or a second timepoint is skipped, not errored.
  • Samples are comparable enough to compare; we do not force rarefaction unless asked.

Environment

  • Trusted, single-user, local input — not a public or adversarial API. No security / sanitisation layer.
  • Paths exist; a missing file simply raises on open. That is our “fail fast”.

10Where Ask-SLM actually writes code

Everything else is a delegate — and honestly, most of even this list is one biom call plus a one-line predicate. The genuinely new code is small: chiefly lineage_table (stitching ete3's three dicts into the attached feature metadata) and the longitudinal selection (the actual analysis). The rest, name only if the repetition truly hurts.

PhaseReal logic we own
ingestAccessors that standardise each source to one schema (rename / coerce; no defensive validation).
buildlineage_table (lineage + rank + ancestor-at-rank per feature); build (pivot, id-align, wrap).
transformthin. The predicates / keys fed to filter & collapse (clade-in-lineage, ancestor-at-rank, thresholds) — each is a single biom.filter/collapse call plus a one-line predicate.
splitconvenience. Partition into dict[value → table] — a small loop over biom.filter; worth it only if per-group sub-tables recur.
analyzecore-features & summary; the longitudinal selection (baseline / shift / volatility).

The line

Libraries answer “how do I compute X?” Ask-SLM answers “given our data, do X reproducibly, in our words, the same way every time.” If a proposed Ask-SLM method is just a rename of one library call, it should not exist — call the library.
