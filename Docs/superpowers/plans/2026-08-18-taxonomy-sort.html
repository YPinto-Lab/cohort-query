1. The measurement that justifies this

Measured against the real mirror on 2026-08-17:

stat_coverage count (preview path)          0.0s  -> 35,681,228
biosamples -> accs                          0.9s
stat coverage of those accs                 1.2s
TAXONOMY read, 16 accs                  1,286.3s  -> 5,164 rows     <- 21.4 MINUTES

An earlier probe read one accession in 1,217.7s. Sixteen accessions cost 1,286.3s. The cost does not scale with the cohort — it is a constant full scan of 13.6 billion rows. There is no index and acc is not clustered, so DuckDB's zone maps (per-row-group min/max) cannot prune anything: every row group's acc range spans the whole alphabet.

A five-sample cohort and a five-thousand-sample cohort both cost 21 minutes. That is the signature of a missing sort order, and sorting is the only thing that fixes it.

This supersedes the earlier hedge. The sort was previously filed as "only worth it if measurements justify it." The measurements now justify it. The user's instinct — that a one-time offline cost is obviously worth paying — was correct.

3. Why the five descriptive columns are simply dropped

Superseded 2026-08-18. An earlier draft of this plan proposed splitting rank, name, ilevel, ileft, iright into a taxa dimension table, gated behind a check that they are functionally dependent on tax_id. That whole apparatus is deleted. The user's standing practice makes it unnecessary: askslm resolves lineage from ete3's current NCBI taxonomy, keyed on tax_id. STAT's own descriptive columns are a stale snapshot and are not the source of truth for anything.

That removes the only genuinely dangerous decision in this plan. NCBI's taxonomy is versioned — Firmicutes → Bacillota, Bacteroides → Phocaeicola, and the nested-set bounds shift whenever the tree is restructured. Preserving STAT's copy would have meant either carrying contradictory names or silently choosing one. We do neither: we keep tax_id, which is stable, and re-derive everything else at read time from a taxonomy that is actually current.

3.1 Prerequisite: STAT lineage must come from ete3 first

This is a live correctness issue, independent of the sort. profiles.py:175 currently does pd.DataFrame({"name": rows["name"], "rank": rows["rank"]}) — it copies STAT's stale names straight into the biom's feature metadata. So today a biom can ship Firmicutes for a taxon NCBI now calls Bacillota. That contradicts the user's stated practice of always refreshing through ete3, and it is wrong whether or not we ever sort anything.

The fix already exists as a planned component: askslm.taxonomy.lineage_table (ete3, ~300 MB database), currently an empty module. STAT's branch of _lineage_of must route through it, keyed on tax_id.

Ordering: ship the ete3 lineage change before the cutover in §8. Until it lands, dropping name/rank from the table would break _lineage_of. Once it lands, those columns are dead weight — which is exactly why this rewrite can discard them without losing anything.

3.2 Open question: keep total_count?

total_count (subtree sum) is not read today; only self_count is. In principle a subtree sum is recomputable from self_count plus ete3 ancestry, so it could be dropped for a further saving.

Recommendation: keep it. It is one bit-packed integer column, the saving is modest, and discarding a number the researcher may want — when recomputing it depends on our ancestry code being right — is the kind of quiet data reduction we have refused elsewhere. The source file is untouched either way, so this is reversible; but there is no reason to spend the reversal.

4. The shape: one narrow sorted table

Today every one of the 13.6 billion rows carries five columns that describe the taxon, not the observation:

acc          VARCHAR   per row   — the run
tax_id       INTEGER   per row   — the taxon observed
total_count  BIGINT    per row   — subtree sum
self_count   BIGINT    per row   — atoms at this node
rank         VARCHAR   per TAX_ID — repeated ~5,700x on average
name         VARCHAR   per TAX_ID — repeated ~5,700x on average
ilevel       BIGINT    per TAX_ID
ileft        BIGINT    per TAX_ID
iright       BIGINT    per TAX_ID

With roughly 2.4M distinct tax_ids across 13.6B rows, each taxon's name and bounds are stored thousands of times over — and per §3 they are stale, unread, and re-derived from ete3 anyway. Dropping them shrinks the scanned bytes before the sort even helps. The target is a single table:

acc          VARCHAR
tax_id       INTEGER
total_count  BIGINT
self_count   BIGINT      — sorted by acc

Then ORDER BY acc on the fact table does two things at once:

  • Pruning — each row group gets a tight acc min/max, so a cohort filter reads only the row groups that can match. This is the 21-minutes-to-seconds change.
  • Compression — sorted acc becomes long runs of identical values, which RLE-compresses hard. Sorting makes the file smaller, not larger.
In a column store, sort order is the index. That is why this plan sorts rather than building an index — see §10.

6. The build

Never mutate /private/pinto-lab/STAT/sra_processed.duckdb. It is shared lab data and not ours to rewrite. Everything below writes a new file and leaves the source byte-identical, opened READ_ONLY. 
ATTACH '/private/pinto-lab/STAT/sra_processed.duckdb' AS src (READ_ONLY);
ATTACH '/private/pinto-lab/tools/just-ask/mirror/sra_taxonomy_sorted.duckdb' AS dst;

-- one statement. The five descriptive columns are simply not selected (§3).
CREATE TABLE dst.tax_fact AS
SELECT acc, tax_id, total_count, self_count
FROM src.tax_raw
ORDER BY acc;

Settings, as in the existing sbatch: SET threads, SET memory_limit='380GB', and SET temp_directory pointed at real storage. Leave preserve_insertion_order at its default so the ORDER BY survives into the written row groups — that ordering is the deliverable.

Do not narrow total_count/self_count to INTEGER to save space. DuckDB already bit-packs integers, so the saving is small, and a run deeper than 2.1 billion reads would silently overflow. Not worth the risk for a few GB.

7. Verification

Run all four before cutover. This rewrites the scientific substrate of every biom the tool will ever produce; "it finished without error" is not evidence.

  1. Row count is exactly preserved — SELECT count(*) FROM dst.tax_fact must equal 13,613,810,995.
  2. The kept columns are bit-identical — for a sample of accessions, the four surviving columns must match the source exactly, both directions empty: 
    WITH rebuilt AS (
  SELECT acc, tax_id, total_count, self_count
  FROM dst.tax_fact
  WHERE acc IN (SELECT unnest(?::VARCHAR[]))
), original AS (
  SELECT acc, tax_id, total_count, self_count
  FROM src.tax_raw WHERE acc IN (SELECT unnest(?::VARCHAR[]))
)
SELECT (SELECT count(*) FROM (SELECT * FROM rebuilt EXCEPT SELECT * FROM original)) AS only_new,
       (SELECT count(*) FROM (SELECT * FROM original EXCEPT SELECT * FROM rebuilt)) AS only_old;
-- both must be 0
    Use the 16 accessions from the timing probe plus a random sample. EXCEPT removes duplicates, so pair it with a plain count(*) comparison per accession — otherwise a row duplicated by the rewrite would pass unnoticed.
  3. Coverage is unchanged — SELECT count(DISTINCT acc) FROM dst.tax_fact must equal stat_coverage's 35,681,228.
  4. It is actually faster — rerun the exact probe from §1 against the new view. Expect seconds. If it is still minutes, the sort did not take and the cutover must not happen — check that row groups really carry tight acc bounds before concluding anything.

8. Cutover and rollback

The package attaches whatever mirror_config.sra_db_path names, under the alias sra. So the cutover is two statements inside the mirror, and the old file is never touched:

-- profiles.py issues SELECT t.*, so the view IS the contract. Four columns now.
-- Requires the ete3 lineage change (§3.1) to have shipped first.
DROP VIEW sra_taxonomy;
CREATE VIEW sra_taxonomy AS
SELECT acc, tax_id, total_count, self_count FROM sra.tax_fact;

UPDATE mirror_config
SET value = '/private/pinto-lab/tools/just-ask/mirror/sra_taxonomy_sorted.duckdb'
WHERE key = 'sra_db_path';

sra_metadata was copied into the mirror at build time, so nothing else depends on the old attachment — the new file needs only tax_fact. Also update sra_schema.py to drop the five field declarations, so the contract matches what the mirror actually serves.

Rollback is one UPDATE and one CREATE VIEW back to sra.tax_raw. Keep the old source file in place until the new path has served real cohorts for a while.

sra_taxonomy fails to resolve on a plain read-only connect — Catalog Error: Table with name tax_raw does not exist!. The ATTACH in adapters.py is load-bearing. It needs a regression test before this cutover, so that a broken attach fails loudly instead of looking like an empty cohort.

9. Fallback if the global sort blows the wall clock

A single ORDER BY over 13.6B rows is one enormous external merge sort. If it exceeds 48 hours or thrashes the spill directory, do it bucketed instead — the result is equivalent for pruning purposes:

  1. Split the acc keyspace into N ranges (prefix-based is fine — SRR/ERR/DRR then numeric bands).
  2. One job per range: … WHERE acc BETWEEN lo AND hi ORDER BY acc into its own part file. These are independent and can run concurrently.
  3. Concatenate the parts in range order with UNION ALL.

Each part is internally sorted and the parts are globally ordered, so every row group still has tight bounds. Bonus: each job is individually restartable, which a 40-hour monolith is not.

10. Deliberately not doing

OptionWhy not
A real index (DuckDB ART) ART is DuckDB's only index type and it is loaded fully into memory every time the database is opened, sized by row count. On 13.6B rows that exceeds node RAM, and the package would pay it on every ATTACH — the interactive path that must stay cheap. ART also targets highly selective point lookups, not the range reads we do. Zone maps from sort order cost nothing at open time and prune the same way.
GPU (cuDF / Sirius) We are I/O-bound, not compute-bound. Anna Shafir's benchmark found GPU 17× faster than CPU DuckDB but still 4× slower than Athena, with her own conclusion that "the main bottleneck remained Parquet file I/O rather than computation." GPU accelerates the part that is not the problem. Revisit only if profiling shows aggregation dominating after the sort.
Staging on compute-node local disk Nodes do have local storage — hpccpu02 shows a 223 GB XFS root with ~156 GB free plus 252 GB /dev/shm — but it is undocumented, SLURM reports TmpDisk=0 so nothing reserves it, and 156 GB cannot hold a 601 GB database. Still the right place for spill if the NFS temp directory proves slow.
Narrowing count columns to INTEGER Saves little after bit-packing; risks silent overflow on deep runs. See §6.

Prerequisites: ≥400 GB free on /private/pinto-lab, and the ete3 lineage change (§3.1) shipped before cutover. Nothing here has been run.
