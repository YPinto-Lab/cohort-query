Workspace & phase organization

How a study lives on disk: one workspace, the five phases as folders, free-form explorations composing shared helpers, and a Markdown lineage layer that the future chat-UI renders. The on-disk information architecture — not the UI.

LOCKED · 2026-06-03 · approved — ready for the implementation plan

0Scope

This spec defines the on-disk organization of a workspace and the form of its code and docs. It does not design the UI.

In: the workspace folder layout; how the five phases map to folders; how data is handed between phases; where code and shared helpers live; the per-folder Markdown doc and the lineage graph it forms.

Out (separate future specs): the chat/web UI (it consumes this structure — renders folders, follows the doc links — but doesn't change it); any new input validation (the project's trust-input / fail-fast stance carries over unchanged).

1The model

A workspace is a study: one folder holding everything. The five phases are stages that hand data to each other through files on disk — each phase reads the previous phase's file and writes its own. Nothing is held in memory between phases; the disk record is the source of truth.

PhaseDoesCadence
ingestpull raw data from any source into the workspaceas sources arrive
buildassemble the one shared community (the building block)once
transform (+ split)named, free-form explorations that shape the communitymany, side by side
analyzemeasure / plot a chosen exploration's resultmany per exploration

The spine

inputs/ → build/community.biom → transform/<exploration>/result/ → analyze/<analysis>/{data,plots}/. Each arrow is a file written to disk and read by the next phase.

2The folder tree

The canonical layout. Every workspace looks like this, so any one reads as designed.

Workspaces/ABX/
├── inputs/                          # ingest: raw dumps land here (one Accessor per source)
├── build/
│   ├── build.py                     # ingest + build — runs ONCE
│   ├── build.md                     # frontmatter: inputs → outputs
│   └── community.biom               # THE shared building block
├── transform/                       # the transform + split phase
│   ├── shared.py                    # (workspace, transform) helpers: exclude_control_subjects, wgs_only
│   ├── no-control_bacteria/          # a named exploration — free-form, ONE script
│   │   ├── explore.py               # imports ../shared.py + the askslm package
│   │   ├── explore.md               # frontmatter: input=../../build/community.biom
│   │   └── result/                   # the community/communities it produced (.biom)
│   └── with-control_viruses/ …
└── analyze/                         # the analyze phase — top-level, grouped by source exploration
    ├── shared.py                    # (workspace, analyze) helpers — shared across ALL analyses
    ├── no-control_bacteria/          # ── all analyses OF this exploration, grouped
    │   ├── braycurtis/
    │   │   ├── analysis.py
    │   │   ├── analysis.md          # input: ../../../transform/no-control_bacteria/result/community.biom
    │   │   ├── data/                 # csv the plots are built from
    │   │   └── plots/                # png
    │   └── alpha-shannon/           # a 2nd analysis OF THE SAME exploration
    │       ├── analysis.py
    │       ├── analysis.md          # input: ../../../transform/no-control_bacteria/result/community.biom
    │       ├── data/
    │       └── plots/
    └── with-control_viruses/ …        # analyses of a DIFFERENT exploration

Why analyze is its own phase, grouped by exploration

Analyze is a top-level phase folder with one shared.py at its root — shared across every analysis. Inside, analyses are grouped one level by their source exploration (analyze/no-control_bacteria/braycurtis/), so the grouping is visible and the helpers stay workspace-wide. Each analysis.md still records the exact input: result it consumes. LOCKED

3Phase-by-phase contract

What each phase reads, writes, and how often. Boundaries are always files.

Phase · folderCodeReadsWritesCadence
ingest
inputs/		 (part of build.py) external sources (SRA, reports, files) raw files into inputs/ as sources arrive
build
build/		 build.py + build.md inputs/ community.biom once · re-run overwrites build/ only
transform
transform/<exploration>/		 explore.py + explore.md · ../shared.py ../../build/community.biom result/*.biom (one, or many if split) per exploration · re-run overwrites that result/
analyze
analyze/<exploration>/<analysis>/		 analysis.py + analysis.md · ../../shared.py one exploration's result/*.biom data/*.csv + plots/*.png per analysis · re-run overwrites that data/+plots/
Idempotency rule LOCKED: a phase only ever writes inside its own folder. Re-running overwrites its own outputs and never touches upstream. So you can re-run any exploration or analysis freely; build is the one run-once root everything depends on.

Shared code splits cleanly by who it's true for.

Scopegeneral — every workspace(workspace, phase) — that phase's scripts only
Versioned withthe codebasethe workspace / data

An exploration or analysis script is free-form glue that imports both: the toolkit for general operations, ../shared.py for this study's repeated steps. LOCKED

Promotion rule LOCKED: write a step inline in the first script. The moment a second script in the same phase needs it, lift it into that phase's shared.py. DRY, but only at the scope where reuse actually happens — never sooner, never wider.

5The doc layer & the lineage graph

Every build/, exploration, and analysis folder carries one .md: a machine-readable header plus two lines of prose. The headers wire the workspace into a graph.

---
kind:    analysis
intent:  Bray-Curtis day0→last shift, per cluster
input:   ../../../transform/no-control_bacteria/result/community.biom
outputs: [data/braycurtis.csv, plots/braycurtis_box.png]
params:  { metric: braycurtis, from: 0, to: last }
---
Per subject, distance between its day-0 and last-day community, boxed by cluster.
Finding: cluster 3 shifts least (mean BC ≈ 0.33).
  • For you: open any folder, read two lines, know what it does and what it used.
  • For the agent: read the header to safely extend a folder without parsing the code.
  • For the future UI: the input:/outputs: fields are graph edges — build → exploration → analysis — so the UI renders clickable file links and a dependency view. Markdown is the source; the UI renders it to HTML at display time.

Format rule

Code = .py. Folder docs = .md with YAML frontmatter (authored, versioned, parsed). Standalone presentation artifacts (like the AbundanceTable explainer) = HTML. The UI turns folder .md into rendered HTML on demand. LOCKED
