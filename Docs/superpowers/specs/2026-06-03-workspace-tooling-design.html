Workspace tooling

Two pieces that make the locked phase structure reproducible by any agent: a one-line askslm.workspace import that ends the path boilerplate, and a scaffold CLI that stamps the exact tree. The conventions move to an agent-agnostic home — no coupling to any one assistant.

0Scope

This spec turns the locked workspace & phase organization into something an agent can reproduce reliably — by replacing convention-followed-by-hand with code and an agent-agnostic rulebook.

In: the askslm.workspace import that resolves a script's paths and shared module; the askslm scaffold CLI that creates the folder tree + template scripts + doc stubs; the AGENTS.md rulebook; migrating the existing ABX_new scripts onto the import to prove it.

Out (separate future specs): the web UI; .biom viewing; any new analysis or domain function. The phase model, folder tree, and the trust-input / fail-fast stance all carry over unchanged.

PROPOSED nothing here is locked until you sign off.

1The problem

The structure is locked, but reproducing it today leans on two fragile things.

FrictionWhat it looks like nowWhy it's fragile
Path boilerplate Every script opens with HERE = Path(__file__)…, a sys.path.insert(…) to find shared, and hand-counted .parents[N] walks to the upstream file and to 0_inputs/. Off-by-one on parents[N] after any folder rename; silent if the path resolves to something wrong. Pure ceremony that hides the five lines of real logic.
Uncodified conventions The phase recipe (numbered folders, result/, .md frontmatter, the promotion rule) lives in your head and in Docs/feature-table-and-library-palette.html. A fresh agent session re-derives it from prose — a missed folder, a wrong number, slightly different frontmatter each time. Drift.
The fix, in one line: make the deterministic parts code (an import + a scaffold command) and put the judgment parts where any agent reads them. The agent stops hand-building structure and just fills in logic.

2The askslm.workspace import

One import replaces the whole header. workspace.phase(__file__) self-locates from the numbered-folder convention and hands back everything the script needs.

Before — every script

import sys
from pathlib import Path
from biom import load_table

HERE = Path(__file__).resolve().parent
sys.path.insert(0, str(HERE.parents[1]))   # find shared
import shared
RESULT = HERE.parents[2] / "2_transform" \
    / "no-control_bacteria" / "result" / "feature_table.biom"
feature_table = load_table(str(RESULT))

After

from askslm import workspace
ws = workspace.phase(__file__)

feature_table = ws.upstream()   # prev phase's .biom
# … shape it …
(ws.result / "feature_table.biom").write_text(   # biom JSON — HDF5 can't
    feature_table.to_json("askslm-no-control_bacteria"))  # round-trip nested lineage

Plain import, so the script still runs with python explore.py. No runner command.

The handle workspace.phase(__file__) returns

MemberIsResolves to (by convention)
ws.inputsPaththe workspace's 0_inputs/
ws.sharedmodulethis phase's shared.py, already imported (no sys.path)
ws.upstream()biom.Tableloads the previous phase's output — see the per-phase table below
ws.resultPaththis script's output dir, created for you — the script writes into it explicitly

Why no ws.save()

An earlier draft had a ws.save(table). It was dropped: unlike upstream() (which resolves which file by phase convention — real logic), a save resolves nothing the script doesn't already hold in ws.result; it only adds the filename and a to_json call. That's a thin delegate, and it's asymmetric — analyze writes CSV/PNG and would never use it. The script writes explicitly instead, so every phase uses ws.result the same way. PROPOSED

How it self-locates — and what each phase gets

It walks up from __file__ to the workspace root (the child of Workspaces/), reads the numbered ancestor folder (1_build → build, 2_transform → transform, 3_analyze → analyze), and wires the rest from the same convention the organization spec locked.

Phasews.upstream() loadsws.result is & script writesExtra
build — (none; build reads files from ws.inputs) 1_build/ — writes feature_table.biom reads multiple input files itself
transform 1_build/feature_table.biom <exploration>/result/ — writes feature_table.biom ws.shared = 2_transform/shared.py
analyze 2_transform/<exploration>/result/feature_table.biom
(matched by the parent folder name)		 <analysis>/result/ — writes CSV/PNG ws.shared = 3_analyze/shared.py

Why this is sound — not magic

The resolver only encodes conventions that are already locked and enforced by the scaffold: numbered phase folders, result/feature_table.biom, and analyses grouped under their exploration name. Nothing is inferred from data — only from the path. If a script sits in a non-conforming place, workspace.phase raises rather than guessing (trust-input / fail-fast). PROPOSED

Is this a real ask-slm function? Yes — path resolution across the phase convention is genuine glue logic that no library provides and it isn't a thin delegate. It earns its place in the askslm package. Loading/saving biom stays a direct biom call underneath.

3The scaffold CLI

Deterministic structure becomes deterministic code. Three commands stamp the exact tree, template scripts (already using workspace.phase), and .md frontmatter stubs — so the agent only fills in logic.

askslm workspace new <name>
   # 0_inputs/  1_build/{build.py,build.md}  2_transform/shared.py  3_analyze/shared.py

askslm transform add <ws> <exploration>
   # 2_transform/<exploration>/{explore.py, explore.md}

askslm analysis add <ws> <exploration> <name>
   # 3_analyze/<exploration>/<name>/{analysis.py, analysis.md}
CommandCreatesTemplate body
workspace new the four phase folders + empty shared.py per phase + a build.py/build.md stub build.py pre-wired to read ws.inputs and write feature_table.biom into ws.result
transform add <exploration>/explore.py + explore.md (frontmatter input: pre-filled to build) ws.upstream() → … → write into ws.result, with comments cueing clade/rank/cohort steps
analysis add <exploration>/<name>/analysis.py + analysis.md (frontmatter input: pre-filled to the exploration result) ws.upstream() → measure → write into ws.result

Wiring

These extend the existing Clients/cli.py and are exposed as a real console script via pyproject.toml ([project.scripts] askslm = "Clients.cli:main"), so askslm … works on the path after pip install -e .. The existing CLI entry, currently unwired, gets wired in the same change. PROPOSED

No run command. Because the import does the path setup, a phase script runs with plain python <script>. Adding a runner would be a second way to do the same thing — omitted to keep the surface small.

4Where the conventions live — agent-agnostic

No coupling to any one assistant. The judgment code can't enforce goes in a rulebook every coding agent reads, and at the point of use inside templates.

HomeHoldsRead by
AGENTS.md (repo root) the law in a few lines: the five phases, the workspace.phase() API, the scaffold commands, the promotion rule, how to name an exploration → links to the bible for the why any agent (Gemini, Cursor, Claude, …) — the cross-tool standard, not CLAUDE.md
Template comments build-vs-transform and the rank/clade/cohort cues, inline at the point of use whoever edits the generated script
Docs/feature-table-and-library-palette.html rationale — the "why", unchanged you, on review

Why AGENTS.md, not CLAUDE.md

The agent driving this workspace can be any tool — it's Gemini today. AGENTS.md is the emerging cross-assistant convention for "instructions any coding agent reads," so the rulebook stays portable. Tool-specific files are avoided. PROPOSED

Acceptance: after migration, re-running the four scripts reproduces the locked numbers (cluster means ≈ 0.41 / 0.38 / 0.33 / 0.33; Mann-Whitney cluster 0 vs 2 p ≈ 0.028). If they don't match, the tooling is wrong, not the science.
