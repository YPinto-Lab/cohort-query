Ask-SLM · Design for review

Agent operating model — make the agent competent

The web UI works and the agent is wired in. But on its first real conversation the agent hand-rolled pandas to build a feature table, dumped a stray .biom in the workspace root, and never touched the askslm package built to do exactly that. The agent has no operating model of the workbench it is supposed to drive. This installs one.

Status: PROPOSED — for review

0The problem, precisely

The symptom is "the agent doesn't know things." The root cause is deeper: the runtime agent has no model of the workbench.

The system prompt today is a six-line hardcoded string (loop.py:12–19). The agent drives only summarize, list_workspace_inputs, and the run_python wildcard. With no model of the workbench, on its first real task it:

  • Hand-rolled pandas → biom.Table instead of using TaxonomyFileAccessor + SRATaxonomySchema, which exist precisely to read that SRA long-form taxonomy.csv.
  • Wrote a stray otu_table.biom in the workspace root, with no idea the model is: author 1_build/build.py → assemble one table → write feature_table.biom into the phase tree.
  • Had no notion of self_count (atomic) vs total_count (cumulative) — it would have built a numerically wrong table even had the mechanics worked.
  • Knew nothing of the code-quality bar the user holds the codebase to.
The fix is not "feed the agent the HTML specs." Those are human-review artifacts — verbose, not agent-optimized. The fix is to design what the agent's operating model is and install it on every turn.

2Architecture — three layers

The operating model is assembled fresh into the system string on every LLM call in loop.py.

LayerSourceLifecycleCarries
1 · Identity preambleinline constantstatic who the agent is; disk is source of truth; prime directive — reuse askslm + established libraries, never reinvent what the package provides, author work as phase scripts.
2 · Operating manualsrc/agent/operating_manual.mdstatic the durable model + a pointer map to canonical sources.
3 · Workspace snapshotrendered from diskregenerated per turn the concrete state of this study: phase tree, intent .md files, inputs, existing .biom outputs.

Why per-turn for layer 3

The workspace changes within a session — the agent writes build.py, then feature_table.biom appears. A snapshot frozen at session start would mislead. The directory walk + reading a few small .md files is cheap, so we re-render each call and the agent always sees ground truth. Layers 1–2 are static; only layer 3 is recomputed.

3Layer 2 — the operating manual

src/agent/operating_manual.md — co-located with the agent runtime, not in Docs/ (which stays the human-review space). Markdown with frontmatter.

It restates only what has no other linkable home, and otherwise routes. Sections:

  • Vocabulary & model — feature table = one biom.Table (counts + sample metadata + lineage); community = one sample's microbes; the five operation kinds (ingest, build, transform, split, analyze).
  • Count semantics (inline, non-negotiable) — self_count is atomic/direct; total_count is cumulative over the clade; never sum total_count across the tree. Build counts from self_count. This stays inline because getting it wrong silently corrupts results.
  • Phase flow — 0_inputs → 1_build → 2_transform → 3_analyze; the build recipe (one Accessor per source → assemble ONE table → write biom JSON, because HDF5 can't round-trip nested lineage metadata); the ws.phase / upstream / result / shared helpers.
  • Pointer map — a table of canonical sources, by repo path, that the agent reads on demand.

Why thin + delegating

A rich self-contained manual maximizes single-shot signal but creates the largest duplication/drift surface — it must be re-synced whenever specs or code change. A thin manual that routes keeps the sources authoritative; the read tools (§5) make the pointers actionable. This is the "build once, single source of truth" choice.

4Layer 3 — the live workspace snapshot

A rendered text block giving the agent concrete ground truth, regenerated each turn.

Contents:

  • the actual phase tree of this workspace (folder/file listing);
  • the contents of the small .md intent files (build.md, explore.md, analysis.md) — small and high-signal;
  • the input files present in 0_inputs/;
  • existing .biom outputs.

Never the giant CSVs (the example taxonomy.csv is 271 MB). The snapshot lists files; it does not read their contents.

This is what ends the "is it inputs/ or 0_inputs/?" floundering from the transcript — the agent sees the real tree every turn rather than guessing. A renderer reads the real layout; if a study predates the canonical tree, the snapshot simply reflects what is there and the manual teaches the agent to reconcile.

5On-demand read tools

Two new read-only tools in session_tools.py that make the pointer map actionable.

ToolSignatureReturns
read_fileread_file(path: str) file text, byte-bounded (see cap below)
list_dirlist_dir(path: str) entries (name, kind, size) for a directory

Safety contract

  • Scope — both resolve relative to the repo root and must stay inside it (reaches Docs/, src/askslm/, this workspace, and ABX_new). Path-traversal guard: resolve() then assert is_relative_to(repo_root), mirroring the existing _safe_* guards in app.py.
  • Hard size cap — read_file reads at most a fixed byte budget and reports truncation. This is mandatory: taxonomy.csv is 271 MB and must never be slurped into context. (Inspecting data shape is what run_python is for.)
  • Read-only — no write/delete capability; writing happens through run_python authoring phase scripts.

Why scope to repo root, not workspace

The pointer map sends the agent to Docs/, src/askslm/, and ABX_new — all outside the active workspace. Repo-root scope is the smallest boundary that covers every pointer while still refusing anything outside the project.

6Vendored code standards

Docs/agent-code-standards.md — repo-resident so the read tool can reach it (clean-code-style lives in ~/.claude/, outside the repo).

A concise distillation, sourced from the user's clean-code-style skill and the project-specific rules that today live only in memory / AGENTS.md:

  • readability is paramount; no lambda — always a named def;
  • no else (guard clauses); functions ≤ ~10 lines, one thing each; ≤ 3 params;
  • one class per file; comments explain why, with the opaque-library-call exception;
  • reuse libraries (skbio / biom / ete3 / pandas) — new custom code only on explicit authorization;
  • keep taxonomy and metadata as two separate DataFrames — never merge;
  • each Accessor reads exactly one source; joins live in Processors;
  • trust input, fail fast — validation only at the Accessor boundary;
  • no backward-compat aliases; compose over duplicate.

Why restating here is consistent with "thin + delegating"

Delegation requires something in-repo to delegate to. These rules currently have no in-repo single home reachable by the read tool, so this file becomes that home. The manual points to it rather than inlining the rules.

7Wiring it together

Where the three layers get assembled, in src/agent/loop.py.

The hardcoded SYSTEM_PROMPT constant is replaced by an assembly function called once per LLM call so layer 3 stays fresh:

# loop.py (shape, not final code)
def build_system_prompt(session) -> str:
    return "\n\n".join([
        IDENTITY_PREAMBLE,                          # layer 1, static
        load_operating_manual(),                    # layer 2, static (read once / cached)
        render_workspace_snapshot(session.workspace)# layer 3, per-turn from disk
    ])

The run loop passes system=build_system_prompt(session) to llm.complete(...) in place of the formatted constant. The new tools register alongside the existing ones in the session registry.

Clean-code shape

Per the standards, the assembly stays small and delegated: build_system_prompt reads as three named steps; render_workspace_snapshot and its helpers each do one thing. The renderer belongs in its own small module (e.g. src/agent/workspace_snapshot.py), one class/concern per file.
