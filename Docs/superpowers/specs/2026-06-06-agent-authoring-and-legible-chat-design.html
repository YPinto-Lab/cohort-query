Agent authoring & legible chat — let the agent write scripts, and quiet the chat

On its second real conversation the agent thrashed to the step limit. It treated run_python as a persistent notebook (it is not — every call is a fresh subprocess), so it hit NameError after NameError and re-read a 271 MB CSV six times. It was told to "author and run phase scripts" but had no tool to write a file or run a script. And every step it took dumped a wall of raw text into the chat. This fixes all three.

0The problem, precisely

Three independent defects compounded into one thrash. They map to issues #1, #4, and #3 from the transcript assessment.

#1 — run_python is stateless, but the agent treats it as a REPL

Each run_python call is a brand-new subprocess (_sandbox_worker.py): it pre-imports pandas/numpy/scipy/skbio/askslm under their own names, os.chdirs into the workspace, and injects existing handles. When the snippet finishes, only new top-level variables whose type is recognized (biom.table.Table, MetadataOverview, DataFrame) survive, as handles. Nothing else persists — not import pandas as pd, not a plain local. The agent assumed continuity, wrote pd.read_csv(...) in a later call, and got NameError: pd three times; it lost an intermediate df and re-read the giant taxonomy.csv to rebuild it, repeatedly.

#4 — the agent is told to author scripts but has no tool to do it

The operating manual says "author 1_build/build.py and run it." The agent's only execution tool is run_python (an ephemeral snippet) and two read tools. There is no way to write a file to the workspace or run a script on disk. So the agent tried to do a whole multi-step build inside one-off snippets — exactly the workflow run_python's statelessness punishes.

#3 — the chat dumps a wall of text every step

For every event, app.py renders _event.html server-side and streams it as an html block; tool results render as <pre>{{summary}}</pre> — the entire stdout, full tracebacks, whole code blocks. Sixteen steps of that is unreadable. The browser already receives a clean typed event for each step (event: tool_call etc.) but ignores it, consuming only the pre-rendered html.

These are the same root cause wearing three hats: the agent has no durable place to put work. Give it one (write a script, run a script), teach it that snippets are ephemeral, and the chat stops being a dumping ground because the heavy work moves into named files surfaced as tidy chips.

2Part 1 — Authoring tools

Two new tools in src/agent/tools/session_tools.py, alongside the existing read_file / list_dir. Read tools are repo-scoped; write/run tools are workspace-scoped.

ToolSignatureDoesReturns
write_filewrite_file(path, content) writes content to path under the active workspace; creates parent directories {path, bytes_written}
run_scriptrun_script(path) runs a .py file on disk as a subprocess (sys.executable), captures output {path, returncode, stdout} (stdout capped)

Safety contract

  • Workspace scope — both resolve relative to session.workspace.root and must stay inside it: resolve() then assert is_relative_to(workspace_root), mirroring the existing _safe_* guards. The agent writes into this study, never the repo at large.
  • write_file auto-creates parents — so the agent can write 2_transform/rarefy/transform.py before the folder exists, matching the phase tree.
  • run_script only runs .py files inside the workspace — reject anything else. Output is byte-capped for context (same spirit as run_python's [-4000:] cap).
  • No handles from run_script — a script's products are files on disk (a .biom, CSVs, plots). They surface through the existing workspace-diff file panel (_files.html), not as in-memory handles.

Why two tools, not one fused "write-and-run"

Separating write from run keeps each tool doing one thing (clean-code standard), lets the agent inspect or re-read a script before running it, and lets it re-run an unchanged script without rewriting it. The chat reads naturally too: "wrote build.py" then "ran build.py" are two honest steps.

Why run_script is a subprocess, not exec in-process

Phase scripts self-locate with workspace.phase(__file__) and import askslm; a real subprocess (same interpreter, askslm already installed in the venv) runs them exactly as the user would from a shell — the disk-is-source-of-truth promise. It also isolates crashes and lets us enforce a timeout, like run_python already does.

3Part 1b — Teaching the execution model (#1)

No new code path — two documentation changes so the agent stops treating run_python as a notebook.

  • Operating manual (src/agent/operating_manual.md) gains a short "How execution works" section stating plainly: every run_python call is a fresh process; imports and plain variables do not carry over; only recognized domain objects survive as handles, which are pre-loaded into later calls by name. For multi-step work, write a phase script with write_file and run it with run_script — that is the durable path. Use run_python only for one-shot inspection (shapes, dtypes, a quick value).
  • run_python docstring (run_python.py) — extend it from "handles are pre-loaded" to spell out the full stateless contract, so the model sees it in the tool schema, not only in the manual.
This is the cheap half of the fix and it depends on the expensive half: telling the agent "write a script instead" only works once write_file / run_script exist. Hence both ship together.

4Part 2 — A legible chat (#3)

Stop streaming pre-rendered walls of text. Render each step client-side as a one-line chip from the typed event the server already emits, with detail one click away.

The events the server emits (unchanged)

The agent loop already yields a typed Event per step, and app.py already streams each as an event: <type> SSE line with a JSON payload. The five types and their payloads:

EventPayloadChip
user{content}none — the browser already shows your message locally
tool_call{tool, args}opens a chip (the verb + target; args feed the detail)
tool_result{tool, summary, is_error}finalizes the chip (fills detail with stdout/output; red if is_error)
assistant_final{content}the agent's prose reply (not a chip)
error{message}a red error row

The verb map (client-side)

A small renderEvent(type, payload) in chat.html maps each tool to a plain verb and a target drawn from its args:

ToolChip labelBehind the disclosure
run_pythonran codethe code (from args.code) + stdout
write_filewrote <path>bytes written
run_scriptran <path>returncode + stdout
read_fileread <path>(none / truncation note)
list_dirlisted <path>entry count
summarizesummarized <handle>the summary
list_workspace_inputslisted inputsthe file list
(unknown tool)the tool nameraw args + summary

Before / after

Today the same step is a multi-line <pre> dump of the whole code and output. After:

· ran code ▸    · wrote 1_build/build.py ▸    · ran 1_build/build.py ▸    · ran code — error ▸

Each chip is a native <details>/<summary>: the verb is the summary line, the full code/output/error is the collapsed body, revealed on click. Nothing is discarded — the complete trace remains in the session log (the "sessions" replay view).

What changes in the plumbing

  • app.py — stop rendering and streaming the per-event _event.html block. Keep emitting the typed event: <type> lines (already there). Keep the trailing _files.html panel as the one event: html block (it is a richer htmx fragment). Retire _streams_to_log and the _event.html template.
  • chat.html — the SSE loop, today only acting on ev==='html', gains a branch: for a typed event, call renderEvent(type, JSON.parse(data)); the html branch stays for the files panel. renderEvent builds the chip DOM with textContent (no innerHTML for model/tool output → no injection). The existing .pending indicator and clearPending() stay; the first chip or final reply clears it.

Why client-side from typed events, not server-rendered html

The server already does the work twice — a typed event and a rendered html block per step. Dropping the html block removes the duplication and the verbosity in one move, and puts presentation where presentation belongs (the browser). The server goes back to emitting facts; the client decides how loud to be.

5Wiring

  • write_file / run_script register in the session registry next to read_file / list_dir; the default-registry test gains both names (same pattern as the read-tools addition).
  • No change to loop.py event flow — it already yields the typed events Part 2 needs.
  • Manual + docstring edits are text-only.

6Testing

  • write_file — writes content under the workspace and creates parents; rejects a path that escapes the workspace (traversal guard).
  • run_script — runs a fixture .py that imports askslm and writes a file, asserts returncode == 0 and the file appears; rejects a non-.py path and a path outside the workspace; caps oversized stdout.
  • Registry — default registry includes write_file and run_script.
  • Chat (template/headless) — assert app.py no longer streams an html block for tool_call/tool_result (only the typed events + the trailing files panel). The chip rendering itself is verified manually in-browser (label, click-to-expand, error styling).
  • Keep green — the existing llm-smoke trajectory test and the read-tool tests.

7Out of scope (deferred follow-ups)

  • #2 / #6 — step limit & redundant re-reads. Raising MAX_STEPS or caching reads is a separate tuning question; the authoring tools should sharply cut step count on their own, so we measure first.
  • #5 — non-canonical workspace trees (e.g. an inputs/ instead of 0_inputs/). Reconciliation of legacy layouts is its own design.
  • A persistent Python kernel. Explicitly rejected — scripts are the durable path.
  • Token-by-token streaming of the agent's final prose. Unchanged from the prior design.
