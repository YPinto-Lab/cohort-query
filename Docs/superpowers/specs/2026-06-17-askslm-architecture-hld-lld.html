Revision 2026-06-20. (1) Flat source model — every DuckDB table is one Source (e.g. METALOG_MOTUS3, METALOG_METADATA). No separate Profiler type; a source's SourceKind (METADATA vs PROFILE) says whether it reconciles or feeds counts. (2) Profiler families — each PROFILE source belongs to a ProfilerFamily = sources sharing both a feature namespace and an abundance estimator (STAT, METAPHLAN, MOTUS).     A. Architecture

    A small layered / hexagonal package. The domain core knows nothing about DuckDB, Gemini, or the filesystem; those are adapters behind ports. The composition root (Runtime) connects concretes to ports. The functions (config, ask, load_plan) are a thin facade — no logic.

    Noam does not call that facade himself. The user surface is an interactive terminal app (askslm) — a driving adapter that sits outside the facade and calls it on his behalf (section C.0). It holds no domain logic: it reads a question, renders the Plan, collects the source choices with arrow keys, and calls run(). The facade remains a real, supported Python API — the terminal app is simply its first and only client.

    Domain depends on nothing. Services depend on domain + ports. Adapters implement ports. This seam lets every service be unit-tested against fakes, and lets the LLM provider, the database engine, or a whole new source be swapped/added without touching the core.

    A.1 Ports

    The Database adapter queries a prebuilt DuckDB over SQL — it never reads raw files. This is a deliberate decision, not an accident of the v1 implementation. The Metalog/SRA files (gzipped TSVs, parquet) are parsed once into a columnar askslm_mirror.duckdb by a separate ETL; the package only ever opens that mirror read-only and runs the LLM's SQL against it. The rejected alternative — read_csv over the raw files at query time — re-parses multi-GB gzip on every call and was ruled out for speed. Build-time reads files; run-time queries DuckDB. Rationale and the A/B/C trade-off: Docs/superpowers/plans/2026-06-18-metalog-duckdb-build.md.

    B. Domain model

    The nouns the package reasons about — the sources, the sample key, and the cohort they form.

    B.1 Sources core model

    One source = one DuckDB table. A database (SRA, Metalog) contributes several. Every source has a kind that decides how multiples of it combine:

    KindSourcesRole in the biomHow multiples combine
    METADATASRA_METADATA, METALOG_METADATAdescribe the samples (sample axis)reconciled per field by precedence (B.4)
    PROFILESRA_TAXONOMY, METALOG_METAPHLAN4_ALL, METALOG_MOTUS3, METALOG_SPIRE_MOTUSfeed the counts (feature axis)union within one family, per sample (whole-column), head wins overlap (B.4, G.3)

    B.2 Families core model

    A profile is comparable to another only when two things match — what its features are and what its values mean:

    • Feature namespace — how features are identified (NCBI taxonomy vs mOTU IDs). Decides whether features can be aligned.
    • Abundance estimator — what the values measure (STAT read-count = sequence abundance; MetaPhlAn/mOTUs coverage = cell abundance). Decides whether values can be pooled (G.3).

    A PROFILE source carries a ProfilerFamily — sources that share both axes, so their values are comparable and can be pooled. A biom unions the same-family sources you name (profile_sources, head first); cross-family sources can never combine:

    ProfilerFamilyNamespaceEstimatorMember sources
    STATNCBI tax_idread-count (sequence abundance)SRA_TAXONOMY (single source)
    METAPHLANNCBI cladecoverage (cell abundance)METALOG_METAPHLAN4_ALL (single source; all taxonomic levels)
    MOTUSmOTU IDcoverage (cell abundance)METALOG_MOTUS3 · METALOG_SPIRE_MOTUS — share mOTU IDs natively
    One biom = one family. The profile_sources Noam names (head first) union their samples into one matrix; the head derives the family, wins any overlapping sample, and supplies lineage. STAT and METAPHLAN are a single Metalog source each; the two mOTUs sources genuinely union (SPIRE adds samples mOTUs3 lacks), and a new same-family source grows the cohort further (G.3). Cross-family mixing is rejected (Materialization guard): STAT and METAPHLAN share a namespace but not an estimator (numbers not comparable — G.3); METAPHLAN and MOTUS share an estimator but not a namespace. Each biom ships its source's native granularity — there is no run() rank knob; Noam projects to a rank himself (G.3).

    Bringing STAT and MetaPhlAn into one biom would need STAT's counts converted to coverage (genome-size normalization) — a future, validated step, not v1. Extension is one row: a new profiler is a new Source tagged with its ProfilerFamily.

    Worked example — PHANTA (why the table, not the tool, sets the family): PHANTA classifies with Kraken2 and re-estimates with Bracken, so its primary output (counts / relative_read_abundance) is read-count = sequence abundance over NCBI taxonomy — the same namespace and estimator as STAT, so that table would pool into the STAT family. PHANTA also emits a genome-length-corrected relative_taxonomic_abundance table (copies_per_million, RPMPM) that approximates cell abundance — a different estimator, hence a different family, not poolable with its own read-count table. One tool, one namespace, two tables → two families: the abundance the chosen table estimates is what decides ProfilerFamily, so a PHANTA Source must name which table it ingests.

    B.3 BioSample key confirmed against the data

    The canonical key is the NCBI BioSample (SAMN…) — the biom's columns are biosamples. The two-hop bridge (Metalog profiles use a study-internal name, not an external accession) is resolved once, at build time, so every table in the mirror already carries a biosample column. The package then sees one primary key across all sources — run-time never re-derives it:

    WhenWhat happens
    Build (ETL, once)resolve profile.sample_alias → metalog_metadata.sample_alias, then spire_sample_name == sra_metadata.biosample; stamp the resolved biosample onto every Metalog table and index it. The two-hop lives here and nowhere else.
    Run (per query)every source — SRA and Metalog — already exposes biosample; joins are single-key. No AccessionNormalizer, no per-query bridge.

    One key, with one honest exception. Because Metalog keeps its own ids (an external accession isn't always 1:1 with a sample) and spire_sample_name is mixed-type, some Metalog samples resolve to no biosample:

    IdentifierRoleNull?
    sample_aliasMetalog's internal PK — always present, unambiguousnever
    biosamplethe cross-source join key (resolved at build, indexed everywhere)NULL for the Metalog-only tail with no external BioSample
    Column-id rule. A biom column is keyed by its biosample when present; for the null tail (Metalog-only, no BioSample — nothing to join to anyway) it falls back to sample_alias. So "one key across all sources" holds for everything that can be shared, without inventing biosamples for orphans.

    B.4 Cohort partition core model

    Discovery runs each source's query — every row already carries its biosample (stamped at build, B.3) — and partitions the cohort by where each biosample appears. That partition is what plan shows and what run() resolves:

    PartitionBiosample appears inMetadata comes fromCounts come from
    SRA-onlySRA query onlySRAa named SRA-side source (only STAT), if listed
    Metalog-onlyMetalog query onlyMetaloga named Metalog source, if listed
    sharedbothmetadata_winning_source decidesthe named profile_sources — head wins overlap

    C. Interface

    What Noam does (C.0, the terminal), what that calls underneath (C.1, the API), and the control flow behind each verb (C.2).

    C.0 User surface — interactive terminal settled 2026-08-16

    Noam never writes Python. He runs one command and answers questions:

    $ askslm
? What cohort do you need? fecal metagenomes from adults with IBD, Western countries
  … 847 samples · 3 studies · MetaPhlAn 62% · mOTUs 91%
? What now? (↑/↓)
  › Run it
    Refine the question
    Choose profile sources
    Save plan and quit

    This replaces the earlier Jupyter-notebook surface. The reason: in the notebook story the user still had to type a line of Python, so "no programming required" was not literally true — the single most-asked question when this design was presented. A terminal session makes it true while keeping the stateful ask → inspect → refine loop that a one-shot CLI cannot provide (each invocation would lose the Plan).

    C.0.1 Libraries decided

    questionary (arrow-key select / checkbox / confirm / text with history — prompt_toolkit underneath) and rich (the plan table). Two dependencies, roughly one hundred lines of glue.

    Explicitly not textual. The reference point people reach for is Claude Code, which is a full-screen TUI: it owns the terminal, redraws, and maintains its own layout engine. That is weeks of work and a permanent maintenance surface. What this design needs — show a table, arrow between options, confirm, repeat — is a line-oriented prompt flow that scrolls like normal terminal output. It feels the same to the user in the ways that matter and costs a small fraction of the effort. Revisit full-screen only if a persistent side panel or live progress across a long download is ever genuinely required. Neither is v1.

    C.0.2 Scope boundary accepted tradeoff

    The session ends when the .biom is written. Downstream analysis and plotting are out of scope — the notebook surface was quietly covering "and then he analyzes it", and dropping it makes that boundary explicit rather than accidental. This is the correct scope for a read-only package whose job is producing a valid cross-study cohort. The answer to "then what?" is: open the biom in whatever you already use.

    The Python facade (C.1) is unchanged and remains public — scripted and reproducible use (load_plan(path).run(...) in a pipeline, with no LLM and no terminal) is still a first-class path.

    C.0.3 First-run configuration Proposed — open

    Dropping the notebook creates a gap this design did not previously have. config(db, llm, llm_key) takes explicit arguments (E.4) — in the notebook story Noam typed them. A user who writes no Python cannot, so the terminal app must source them itself. That mechanism does not exist yet.

    Proposed, smallest thing that works: on first run, prompt for the database path and LLM key, write them to ~/.askslm/config.toml, and read that file on every later start (environment variables override it, so CI and the lab server need no file). Subsequent runs prompt for nothing.

    Deliberately not settled here because it is coupled to the one genuinely open product question: where the prebuilt DuckDB is hosted and who pays for it (lab server / Zenodo / object store / user-built). If the package ends up fetching the mirror itself, first-run config grows a download step and db_path gains a default — so decide the hosting first, then this. Settings (E.4) is unchanged either way: whatever the app reads, it still calls config() with the same three values.

    C.1 Public API revised

    This is the layer underneath C.0 — what the terminal app calls on the user's behalf, and what a script calls directly. Every prompt in C.0 maps to exactly one call here; nothing in the terminal app has a counterpart the API lacks.

    Two verbs. ask() understands the question and previews the cohort — no source choices, no biom presupposed. run() materializes a biom and is the only place the sources are named — the profile_sources to union (all one family, head first) and which METADATA source wins ties. There is no rank knob — bioms ship native granularity (C.1.4).

    C.1.1 Calls

    Shown as a script, which is how a pipeline uses it. In the terminal app (C.0) the same sequence is driven by prompts — config() from the config file at startup, ask() from the typed question, run() on confirmation.

    # configure once
askslm.config(db="/mnt/lab/metalog_sra.duckdb", llm="gemini", llm_key=os.environ["..."])

# understand + preview (one LLM hop + cheap COUNTs). Persists the plan to disk.
plan = askslm.ask("fecal metagenomes from adults with IBD, Western countries", save="plans/ibd.json")
print(plan)                # the show-your-work below; stats-only users stop here

# one MetaPhlAn source today — a bare Source is fine (normalized to a one-element list):
table = plan.run(profile_sources=askslm.Source.METALOG_METAPHLAN4_ALL,
                 metadata_winning_source=askslm.Source.METALOG_METADATA,   # default
                 out="cohort.biom")                                # prints the overview below, returns a biom.Table

# union same-family sources into one biom — head first, head wins overlapping samples:
plan.run(profile_sources=[askslm.Source.METALOG_METAPHLAN4_ALL,           # head: family + lineage + tie-break
                          askslm.Source.SOMENEW_METAPHLAN],               # adds the samples Metalog lacks
         out="cohort_metaphlan_union.biom")

# reproduce later — same cohort, a different family, no LLM call:
askslm.load_plan("plans/ibd.json").run(profile_sources=askslm.Source.METALOG_MOTUS3, out="cohort_motus.biom")

# same cohort, STAT family — ships self_count at every rank; project to a rank yourself with StatProfile:
stat = askslm.load_plan("plans/ibd.json").run(profile_sources=askslm.Source.SRA_TAXONOMY, out="cohort_stat.biom")
askslm.StatProfile(stat).relative_abundance(rank=askslm.Rank.GENUS)   # per-rank RA + Unclassified bucket (G.3.4)

    C.1.2 plan render

    Render contract (changed with the terminal surface). The plan renders through __str__ / PlanView — plain text, terminal-first. There is no _repr_html_: the notebook surface is gone, so the HTML repr it would have needed is not built. The terminal app styles the same PlanView with rich; a script gets the identical content from print(plan). One view object, two renderers, no divergence.

    The headline most queries need: what was understood, how big the cohort is, and — per family — what each profile source covers and how many samples it adds that no other same-family source has (its unique contribution). That +unique column is the whole point: it tells Noam when listing several same-family sources grows the biom (and when it adds nothing). Families are never pooled.

    C.1.4 Build overview

    Materialization is not silent: run() returns a one-screen summary of what it actually built alongside the biom.Table, so Noam sees the drops and the provenance without inspecting the file. Same rule as C.1.2 — the value object is built here, the terminal app renders it, and it is the last thing the session prints before exiting.

    Built  cohort_metaphlan_union.biom   (biom JSON)

    family           METAPHLAN   (coverage → relative abundance)
    samples          228             (union of the named sources ∩ cohort)
    features         1,432 clades (all levels)
    counts           METALOG_METAPHLAN4_ALL 207 (head)  ·  SOMENEW_METAPHLAN +21 new  ·  0 overlap re-used

    The run() knobs. profile_sources is one or more PROFILE sources of one family (head first — it derives the family and wins overlaps); metadata_winning_source is a METADATA source — both checked on construction (E.2). There is no rank knob; bioms ship native granularity. One plan materializes many ways; adding a database, profiler, or family never moves ask()'s signature.

    • The current biom build path is wrapped by BiomFactory; assembly rules unchanged.
    • Reconciliation keeps two DataFrames (standing rule): metadata and lineage never merge.

    Accession = NewType("Accession", str)   # canonical (biosample-level) id — the join key

class SourceKind(Enum):
    METADATA = "metadata"          # reconcilable across sources by precedence (per field)
    PROFILE  = "profile"           # feeds counts; lives in a ProfilerFamily

class ProfilerFamily(Enum):       # shared namespace AND estimator → values comparable
    STAT      = "stat"            # NCBI tax_id · read-count (sequence abundance)
    METAPHLAN = "metaphlan"       # NCBI clade · coverage (cell abundance)
    MOTUS     = "motus"           # mOTU IDs · coverage (cell abundance)

class Unit(Enum):
    COUNTS   = "counts"             # normalized to RELATIVE on materialization
    RELATIVE = "relative"

@dataclass(frozen=True)
class SourceSpec:
    database: str                # provenance: "sra" | "metalog"
    table: str
    kind: SourceKind
    family: ProfilerFamily | None = None      # set for PROFILE sources
    unit: Unit | None = None                  # native unit of a PROFILE source
    lineage_column: str | None = None         # set for PROFILE sources

@dataclass(frozen=True)
class ResearchQuestion:
    text: str                    # the whole question; source-agnostic

@dataclass(frozen=True)
class SourceQuery:
    source: Source
    sql: str

@dataclass(frozen=True)
class Translation:                # LlmBackend output, before any DB hit
    interpretation: QueryInterpretation
    queries: tuple[SourceQuery, ...]    # one per source — add a source, add an entry

@dataclass(frozen=True)
class CohortPreview:              # the show-your-work numbers
    by_metadata_source: dict[Source, int]            # the partition — who has the sample
    shared: int                  # in >1 metadata source — the overlaps
    union: int
    by_profile_source: dict[Source, int]             # coverage per PROFILE source
    profile_unique_in_family: dict[Source, int]      # samples a source adds that NO same-family source has → tells Noam unioning grows the biom (C.1)
    profile_family_union: dict[ProfilerFamily, int]  # biom size if you union every source in the family; ints only, so the persisted plan stays small

class Rank(Enum):                   # taxonomic ranks — read-side only (StatProfile.relative_abundance); no run() rank knob
    SPECIES = "species"
    GENUS   = "genus"
    FAMILY  = "family"
    ORDER   = "order"
    CLASS   = "class"
    PHYLUM  = "phylum"

@dataclass(frozen=True)
class Materialization:           # the run() choices, grouped + validated
    profile_sources: tuple[Source, ...]     # head first; all one ProfilerFamily
    metadata_winning_source: Source

    def __post_init__(self):
        require(bool(self.profile_sources), "profile_sources must name at least one source")
        require(all(s.kind() is SourceKind.PROFILE for s in self.profile_sources), "every profile source must be a PROFILE source")
        require(self._one_family(), "all profile_sources must share one ProfilerFamily")
        require(self.metadata_winning_source.kind() is SourceKind.METADATA, "metadata winner must be a METADATA source")

    def head(self) -> Source:
        return self.profile_sources[0]            # derives the family, wins overlapping samples, supplies lineage

    def family(self) -> ProfilerFamily:
        return self.head().spec().family         # the biom's one family, derived from the head

    E.4 Composition root

    The composition root is the runtime.py module, not a class — it has two factories and no state worth wrapping in an object. config() stores the validated Settings once; the factories read it.

    Settings is constructed from explicit arguments and knows nothing about config files or the environment. Whoever calls config() sources the three values — a script passes them literally, the terminal app reads them from its own store (C.0.3, still open). Keeping that outside Settings is what lets the validation stay a plain fail-fast __post_init__.

    E.5 Cohort

    There is no run-time normalizer: the biosample key is materialized at build (B.3), so every query already returns it. Accession is just the resolved biosample (or the sample_alias fallback for the null tail). Cohort is therefore pure set logic over keys that arrive ready:

    @dataclass(frozen=True)
class Cohort:
    by_source: dict[Source, frozenset[Accession]]    # metadata sources that returned each biosample

    def union(self) -> frozenset[Accession]:
        return frozenset().union(*self.by_source.values())

    def shared(self) -> frozenset[Accession]:
        return self._appearing_in_more_than_one()      # the overlaps

    def only(self, source: Source) -> frozenset[Accession]:
        others = self.union() - self.by_source[source]
        return self.by_source[source] - others

    Turning a question into a saved, reviewable Plan — one LLM hop, then cheap preview counts.

    F.2 Plan

    The Plan is a two-step, reproducible artifact: ask() builds and persists it; run() materializes it — any number of times, with different winners or rank. load_plan re-enters at the persisted state without touching the LLM.

    @dataclass(frozen=True)
class Plan:
    question: ResearchQuestion
    translation: Translation
    preview: CohortPreview
    error: str | None = None

    def run(self, profile_sources: Source | Sequence[Source], out: Path,
            metadata_winning_source: Source = Source.METALOG_METADATA) -> biom.Table:
        self._guard_runnable()
        request = Materialization(profile_sources=_as_tuple(profile_sources),   # a bare Source → one-element tuple
                                  metadata_winning_source=metadata_winning_source)
        return runtime.cohort_builder().build(self, request, out)

    def _guard_runnable(self):
        if self.error is not None:
            raise TranslationError(self.error)

    def __str__(self) -> str:                # terminal-first; no _repr_html_ (C.1.2)
        return PlanView(self).render()

    The source choices are not stored on the Plan — they are run() arguments, so one persisted plan materializes many ways. run() bundles them into a validated Materialization so CohortBuilder.build(plan, request, out) stays at three params. The module-level runtime.cohort_builder() factory is reached directly because load_plan(path).run() must work from a bare file — the one Settings set at config() time is module state (E.4).

    class PlanRepository:
    def __init__(self, root: Path):
        self._root = root

        target.write_text(self._encode(plan))

    F.3 Ask & preview

    class AskService:
    def __init__(self, translator: Translator, previews: CohortPreviewBuilder, repository: PlanRepository):
        self._translator = translator
        self._previews = previews
        self._repository = repository

    def ask(self, question: ResearchQuestion, save: Path | None) -> Plan:
        translation = self._translator.translate(question)
        plan = self._planned(question, translation)
        self._repository.save(plan, save)
        return plan

    def _planned(self, question: ResearchQuestion, translation: Translation) -> Plan:
        preview = self._previews.preview(translation)
        return Plan(question=question, translation=translation, preview=preview)

    CohortPreviewBuilder runs cheap aggregates only: per metadata-source accession counts and the overlap (shared) size, plus — for every PROFILE source — the cohort biosamples it covers (a SELECT DISTINCT biosample, ids only). From those per-source sets it derives, per family, each source's unique-in-family count and the family union size, then stores just the ints on CohortPreview (the sets are discarded — they never enter the persisted plan). This is what powers C.1's +unique column. It is also where invalid SQL is caught — the query fails and the Plan is returned carrying error, so review still renders and run() refuses.

    G. Build engine

    What run() drives: discover → reconcile → assemble the biom.

    G.1 Cohort engine

    class CohortBuilder:
    def __init__(self, discovery: CohortDiscovery, profiles: ProfileReconciler,
                 metadata: MetadataReconciler, factory: BiomFactory):
        self._discovery = discovery
        self._profiles = profiles
        self._metadata = metadata
        self._factory = factory

    def build(self, plan: Plan, request: Materialization, out: Path) -> biom.Table:
        cohort = self._discovery.discover(plan.translation.queries)
        matrix = self._profiles.read(request, cohort.union())
        metadata = self._metadata.reconciled(cohort, request.metadata_winning_source)
        table = self._factory.build(matrix, metadata.restricted_to(matrix.accessions()))
        return self._written(table, out, dropped(cohort.union(), matrix.accessions()))

    CohortDiscoverydiscover(queries) -> Cohortrun each query (rows already carry the build-stamped biosample), group by metadata source into a Cohort that knows its overlaps. No normalization step.
    ProfileReaderread(source, accessions) -> ProfileColumnspull one PROFILE source's table; columns are the samples that actually have it.
    ProfileReconcilerread(request, accessions) -> ProfileMatrixover the named request.profile_sources (all one family): read each via ProfileReader at native granularity, fold per sample in list order (head wins overlap, each source adds its disjoint samples). Full pipeline in G.3.
    MetadataReaderread(source, accessions) -> DataFrameread ONE metadata source's frame for the cohort — the mirror of ProfileReader.

    G.2 Metadata merge

    There are two METADATA sources, so reconciliation is just "winner wins, the other fills gaps." The chosen winning_source heads a combine_first; the other source fills only the fields it leaves empty. No precedence table — with two sources the winner fully determines the result, and the single other source has no peer to tie with.

    class MetadataReconciler:                                # the only reconciler — profiles are one source
    def __init__(self, reader: MetadataReader):
        self._reader = reader

    def reconciled(self, cohort: Cohort, winning_source: Source) -> ReconciledMetadata:
        winner = self._reader.read(winning_source, cohort.union())
        others = [self._reader.read(s, cohort.union()) for s in cohort.by_source if s is not winning_source]
        return ReconciledMetadata(self._folded(winner, others))

    def _folded(self, winner: pandas.DataFrame, others: list[pandas.DataFrame]) -> pandas.DataFrame:
        return reduce(combine_first_onto, others, winner)   # winner wins; each other only fills gaps

    Frames indexed by Accession; combine_first is exactly "left wins, right fills," so the winner heads it and the other source fills only the gaps. No else, no lambda — combine_first_onto is a named module function. A third metadata source is the only thing that would reintroduce an explicit order among non-winners; that day, add a precedence tuple — until then it is speculative.

    G.3 Profiles → matrix

    A biom holds one profiler family; ProfileReconciler turns the profile_sources Noam names — all in that family — into a single matrix by unioning their samples. The family is what makes the union valid (shared namespace + estimator), and is also why STAT and MetaPhlAn can't be pooled (the abundance estimator). That argument first, then the pipeline.

    Why union same-family sources. Same namespace + same estimator means the columns are directly comparable, so one biom can take whole columns from several family sources and grow its sample set — exactly what you want when a new source (say SomeNewSource, also MetaPhlAn) brings samples Metalog lacks. For a sample present in more than one source the head (first in profile_sources) wins — low-stakes, since same-profiler columns agree. Today METAPHLAN and STAT are a single Metalog source each, while the two mOTUs sources genuinely union (SPIRE adds samples mOTUs3 lacks); a new same-family source (e.g. SomeNewSource) extends it further.

    G.3.1 Why single-family

    MetaPhlAn maps reads to clade-specific marker genes, estimates each clade's coverage, corrects for marker length, and reports each clade as a fraction of the community — values sum to ~100% within a rank over the classified fraction. It measures cell abundance, not read counts. STAT (sra_taxonomy) instead assigns reads across the whole genome (k-mer matching) and reports read counts per NCBI tax_id — so its values scale with genome length: sequence abundance. Same biology, two different quantities. mOTUs is coverage-based like MetaPhlAn (cell abundance) but in a different namespace (mOTU IDs). Hence three families, no cross-family pooling.

    G.3.2 Worked example

    Both tools start from the same raw reads — the difference is what they count. One sample, species A and B in equal cell abundance, but A has a 6 Mb genome and B a 2 Mb genome (3× smaller). Same sequencing, so reads scale with genome length:

    StepSpecies A (6 Mb)Species B (2 Mb)
    reads (∝ cells × genome length)6,0002,000
    STAT = reads ÷ classified total (8,000)6000 ⁄ 8000 = 75%2000 ⁄ 8000 = 25%
    marker coverage = reads ÷ length (∝ genome)6000 ⁄ 6 = 1000×2000 ⁄ 2 = 1000×
    MetaPhlAn = coverage ÷ Σcoverage (2000)1000 ⁄ 2000 = 50%1000 ⁄ 2000 = 50%
    Same sample, same reads — STAT says 75/25, MetaPhlAn says 50/50. A's larger genome soaks up proportionally more reads; MetaPhlAn's division by marker length removes that, recovering the true 50/50 cell ratio. A STAT proportion and a MetaPhlAn proportion are not interchangeable — so STAT and METAPHLAN are different families and never share a biom. Each is materialized on its own.

    G.3.3 Pipeline

    Each named source is read in its native values — STAT as self_count per tax_id (every NCBI rank; the atoms), MetaPhlAn as native per-rank relative abundance — with no build-time roll-up or normalization. The per-source columns combine only at fold_by_sample — whole columns, in list order, the head winning any sample two sources share. A sample is never a blend of two tools, and the biom keeps each source's native granularity (rank + lineage on every feature) so Noam projects to any rank himself (G.3.4).

    G.3.4 Granularity & the STAT relative-abundance view

    askslm does not collapse to a rank and has no build-time rank knob. Each biom ships its source's native granularity, with rank + lineage on every feature, so Noam decides what to look at:

    • STAT — self_count per tax_id at every NCBI rank. Self-counts partition the reads (each read assigned to exactly one node), so the column is summable: total_count(node) = Σ self_count over its subtree. Counts feed read-count tools (DESeq2, ALDEx2, rarefaction); any relative abundance is derivable.
    • MetaPhlAn — native per-rank relative abundance (all levels); each rank already sums to ~1. Compositional tools (MaAsLin, LEfSe, CLR) consume it directly, and a single-rank view is a row filter.

    Rolling coarser is Noam's to do — but the one STAT projection that is fiddly to get right ships as a read-side helper: per-rank relative abundance with an honest Unclassified bucket for the reads stranded above the chosen rank (STAT only; for MetaPhlAn it is a row filter). It never mutates the stored biom:

    class StatProfile:                                   # read-side view over a STAT self_count biom
    def __init__(self, counts: biom.Table):
        self._counts = counts                        # features = tax_ids (all ranks) · value = self_count

    def relative_abundance(self, rank: Rank) -> biom.Table:
        clades   = roll_up_to(self._counts, rank)                      # rank-R clade = Σ self_count over its subtree
        complete = add_unclassified_bucket(clades, self._classified)   # + reads stranded above R, so nothing is dropped
        return to_proportions(complete, self._classified)            # ÷ classified reads per sample → each sample sums to 1

    @property
    def _classified(self) -> pandas.Series:
        return self._counts.sum(axis="sample")              # Σ self_count = total classified reads, per sample

    The rank argument is a read-side projection, not the old build knob: relative abundance only sums to 1 within a rank, so the table must name one — the same biom yields a species table and a genus table from two calls. total_count is never stored; it is the subtree sum, recovered on demand. (Rank is the taxonomic-rank enum, now used only here at read time — there is no run() rank argument.)

    class ProfileReconciler:
    def __init__(self, reader: ProfileReader):
        self._reader = reader

    def read(self, request: Materialization, accessions: frozenset[Accession]) -> ProfileMatrix:
        columns = [self._reader.read(s, accessions) for s in request.profile_sources]
        return ProfileMatrix.fold_by_sample(columns)   # native values, one family · list order: head wins overlap, others add their samples

    The profile_sources list is the precedence — no DEFAULT_PRECEDENCE table; the head is first, the rest follow in the given order. Materialization has already checked they share one family, so cross-family mixing can't reach here. There is no roll-up and no normalization in the build — each source is stored at native granularity; fold_by_sample is a named function — no lambda.

    G.3.5 Roadmap future

    To build one biom from STAT and MetaPhlAn (more samples, one estimator), STAT's read counts would be converted to coverage — divide by genome length → cell abundance — moving it into the METAPHLAN family. That also needs the feature ids reconciled, tax_id → clade, via MetaPhlAn's own metaphlan_clades crosswalk (clade_name, lineage, NCBI_taxids; named clades carry a tax_id, SGB clades don't → MetaPhlAn-only). Both steps are approximate and need validation, so they are out of v1. The same crosswalk also lets a researcher align taxa across a separately-built STAT biom and MetaPhlAn biom.
