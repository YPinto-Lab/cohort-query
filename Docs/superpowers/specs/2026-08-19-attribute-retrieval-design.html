Attribute key retrieval accepted 2026-08-19

Making the ~35,000 phenotype fields hidden inside jattr reachable, without putting them in the prompt.

2026-08-19 · supersedes the "flatten jattr into columns" proposal · closes the open decision in HLD F.1

1. The question that found this

The first real session, against the real mirror:

? What cohort do you need? IBD fecal metagenomic with calprotectin
  ✗ Could not translate that into a query.
    no metadata field records calprotectin levels

The model was right, and the answer was wrong. No column records calprotectin. The data is nonetheless there — 2,342 runs carry it inside jattr, the SRA per-sample attribute blob:

"body_site_sam": ["UBERON:feces"], "calprotectin_sam": "435.0",
"cd_behavior_sam": "Stricturing (B2)", "cd_location_sam": "Ileal..."

That is exactly the IBD phenotype a researcher wants, and it is invisible to the model because nothing in the prompt names it.

2. Why flattening does not fix it

The obvious fix is wrong, and the numbers say so. The standing proposal was to explode jattr into real columns. A census of the keys kills it:
  • 35,768 distinct keys in a 200,000-row sample alone.
  • calprotectin_sam appears in 2,342 of 39,100,115 runs — 0.006%.
  • The frequent keys are technical noise: primary_search, bytes, bases, run_file_create_date.
Any top-N flattening keeps the junk and drops the phenotype. Interesting clinical fields are rare by nature — that is what makes them interesting. Flattening the common keys yields a bigger prompt and still no calprotectin.

3. The design: retrieve, don't enumerate

Schema linking is supposed to give the model the relevant schema, not all of it. We have been doing the opposite. So:

  1. Index every key once, at ETL. One table, attribute_keys, mapping each jattr key to how many runs carry it and a few real sample values.
  2. Search it per question, at ask(). Terms from the question are matched against key names; only the matches enter the prompt.
  3. Teach the model the accessor. The prompt explains json_extract_string(jattr, '$.key'), and that values are strings so numbers need TRY_CAST.
"IBD fecal metagenomic with calprotectin"
   -> search attribute_keys for 'calprotectin'
   -> found: calprotectin_sam (2,342 runs, e.g. "435.0")
   -> prompt gains ONE line
   -> WHERE TRY_CAST(json_extract_string(jattr, '$.calprotectin_sam') AS DOUBLE) IS NOT NULL

This shrinks the prompt rather than growing it: a handful of matched keys per question instead of a blob nobody can read. And it fixes the whole class of question permanently — any of the 35,768 keys becomes reachable the moment a researcher names it.

This closes the open decision in HLD F.1, which weighed shipping top-N values plus ILIKE against "a value-lookup step — the model queries candidate spellings before committing to SQL — which makes translation two LLM hops instead of one". The retrieval here costs zero extra LLM hops: it is a local index lookup before the single existing hop. The recommendation was to measure before adding a second hop. We measured, and we do not need one.

4. Verified mechanics

Everything below was run against the real mirror before the design was written.

QuestionAnswer
Does json_extract_string work on jattr? Yes — 1.7s, returns ('SAMEA19576168', '435.0', 435.0) with TRY_CAST(... AS DOUBLE).
Cast jattr to MAP and unnest? No. MAP(VARCHAR,VARCHAR) and MAP(VARCHAR,JSON) both return zero rows — some values are arrays. Do not use this.
Cost of unnest(json_keys(jattr)) 1s per 20k rows → ~32 min for 39.1M. Acceptable, one-time.
Cost of keys and sample values in one pass 36s per 20k rows → ~19 hours. Rejected.

Consequence: counts are computed over all rows (the number is a fact the researcher may act on); sample values are computed over a sample (they only illustrate format). Two passes, not one.

5. Deliberate limits

  • Matching is lexical, not semantic. "calprotectin" finds calprotectin_sam; "gut inflammation marker" will not. A synonym layer or embedding search is the obvious extension, and is deliberately not v1 — measure whether the simple thing fails first.
  • attributes (the STRUCT(k,v)[] column) is not indexed. It carries the same information as jattr in a different shape. One is enough.
  • Metalog is not indexed. Its metadata is already flat and wide (205 real columns), so the catalog already exposes it.
  • No cohort-size guarantee. A key present in 2,342 runs will produce a small cohort. That is the truth about the data, not a defect — the preview reports it and the narrow warning fires.
