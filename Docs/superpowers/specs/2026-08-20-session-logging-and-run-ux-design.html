Session run-directory, logging & run UX accepted 2026-08-20

Every question gets a folder on disk; every run leaves a log; "Run it" submits a real SLURM job instead of running on the login node, and survives your terminal closing.

2026-08-20 · touches src/askslm/cli/session.py, src/askslm/build.py, src/askslm/adapters.py, src/askslm/runtime.py, and adds src/askslm/cli/worker.py · no change to Plan/Materialization's public shape

1. The problem this fixes

A real session on the server, right after picking sources and confirming output:

? What now? Run it
? Which feature space? STAT
? Which sources? (order = precedence) done
? What now? (Use arrow keys)

Nothing between "done" and the next menu tells you a multi-minute build ran, where it wrote, or whether it's safe to assume it finished. Separately: nothing survives a session except what you manually choose to Save plan and quit, and there is no record at all of what the LLM was actually sent or what SQL actually ran — the only way to find out is Show the SQL and overlap, and only for the current plan, only while the session is still open.

Worse than the missing feedback: "Run it" runs on the SLURM login node. askslm is invoked directly at a [user@slurm-login1]$ prompt, and today plan.run(...) executes CohortBuilder.build — DuckDB reads over a multi-hundred-GB mirror — right there in that shell, on shared login-node CPU, with no tmux/screen, and no job scheduler involved at all. A closed terminal or a dropped SSH connection kills the build outright, and every login-node build competes with everyone else's interactive `ssh` sessions on a node that isn't meant to run compute. This is the part of the redesign that matters most: "Run it" has to become a real SLURM job.

2. Plan folder: one per question

The instant _session() reads a question (first ask, "Refine the question", or "Ask new question"), before calling askslm.ask(), it creates:

plans/<YYYYMMDD_HHMMSS>/
  log.txt      # created immediately -- captures the run even if ask() throws
  plan.json    # written only if ask() returns with plan.error is None
  cohort.biom  # default "Run it" output target; still overridable

Every question is a new folder — refining keeps the text pre-filled but is still a new ask() call, so it gets a new timestamp. The previous folder is left on disk exactly as it was; nothing merges across refinements. No collision handling is added for two questions in the same second — that has never happened in practice and mkdir would just raise if it did.

3. Logging: what goes in log.txt

Stdlib logging, one file handler per plan folder, attached to the askslm logger when the folder is created and removed (not just replaced) when the next one is. Three call sites feed it:

  • cli/session.py — one logger.info(...) beside every questionary .ask(): which prompt, what was answered. This is the only new logging call site that is CLI-specific; it is what makes the whole session replayable from the log alone.
  • adapters.py, GeminiBackend — prompt text, raw response text, and elapsed time around translate, expand, and repair. These already exist as three separate methods on one class; logging wraps each, it does not change what they do.
  • adapters.py, DuckDbConnection.query — the SQL string, row count, and elapsed time. One hook, because every SQL execution in the system — attribute retrieval, cohort discovery, profile reads — already funnels through this one method on the Database port. No other file needs a logging call for SQL to be fully captured.
This is observability, not new behavior: nothing here changes a return value, a retry count, or an error path. CannedLlmBackend and any test double are untouched — logging lives in the concrete adapters, not the ports, so the fakes the test suite injects keep running with no log file and no handler at all.

4. Auto-save replaces manual save

Immediately after askslm.ask() returns, if plan.error is None, the session writes plan.json into that question's folder itself — the same Plan.save that "Save plan and quit" used to call explicitly. A translation failure or an error that survived the one repair attempt is not saved as a plan; log.txt is the only record of that attempt, which is the point of writing it before the outcome is known.

5. Menu

The SQL and overlap are already-computed data the moment ask() returns successfully (they come from plan.translation.queries and plan.preview, both already in hand) — gating them behind a menu click added a step for information that costs nothing to show. _ask()'s success path now prints interpretation, preview line, narrow warning, per-source SQL, and the overlap table together, and Show the SQL and overlap is removed from the menu:

5.1 askslm run is renamed askslm load

The subcommand that replays a saved plan with no LLM hop is renamed: askslm run plans/<ts>/plan.json becomes askslm load plans/<ts>/plan.json. This is purely a rename at the main() dispatch in session.py — it disambiguates the CLI verb from the in-session Run it menu choice, which now means something with real weight (submit a SLURM job) rather than "replay a file." Plan.run(...), the Python API method, is untouched — this only renames the shell-level subcommand.

5.2 askslm load gets the same menu — and reattaches to a running job

_replay() currently builds once and exits — no menu at all. It now creates its own timestamped plans/<ts>/ folder for log.txt and the default cohort.biom target (the loaded plan.json stays wherever it was; loading does not rewrite or move it), then loops on a menu scoped to what a loaded plan can actually do — there is no question to refine, so no LLM-related choices appear:

? What now?
 » Run it
   Discard
   Quit

Run it lets you rebuild the same loaded plan with a different feature space/source combination without re-invoking askslm load from the shell. Discard deletes this load's folder (and any biom it wrote) — never the original plan.json path, which is a caller-owned input, not something this run created; if a job is still running in that folder, Discard cancels it first (scancel) rather than deleting files out from under a live SLURM job.

This is also how you open the Run progress view from another terminal — the whole reason a login-node process must not be the thing tracking job state. askslm load plans/<ts>/plan.json checks that folder for job.id: if a job was submitted from it and is still running, loading drops straight into the live watch view (§7.2) instead of the menu above, from any shell, any time, with no session state carried over — everything needed to find the job and tail its log lives in the plan folder itself.

6. Skip a menu that has only one answer

_run's two prompts each become a no-op when they'd only ever offer one choice:

  • _families(plan) — when the cohort covers exactly one ProfilerFamily, skip the questionary.select and use it directly.
  • _sources_of(family) restricted to sources the cohort actually covers — when exactly one remains, skip the questionary.checkbox and use it directly.

Silently skipping a step is confusing on its own — the transcript would jump from "Run it" to a build with no visible reason. So each auto-pick prints one line before the build starts, in the same header that already announces the output path:

Building cohort -> plans/20260820_143012/cohort.biom
  feature space: STAT (only option)
  sources: METALOG_MOTUS3 (only option)
  [1/3] discovering cohort...        12.4s
  ...

When a prompt has more than one real choice, it is asked exactly as today — this only removes the click when there was never a decision to make.

7. "Run it" submits a SLURM job

The default "Write to" answer in the source-picking prompt changes from feature_table.biom to <plan folder>/cohort.biom. Once family, sources, and output path are settled, _run asks one more thing before submitting:

? Use GPU acceleration for this build? (y/N)

defaulting to No. This is a per-build choice, not a session-wide setting (§7.1) — a small mOTUs cohort gains nothing from reserving a GPU node; a large STAT build might.

7.0 The worker: a new, small, LLM-free entrypoint

A new module, src/askslm/cli/worker.py, is what the SLURM job actually runs — python -m askslm.cli.worker --plan <plan.json> --family <name> --sources <a,b,c> --out <path> --db <mirror> [--gpu]. It loads the plan, calls askslm.config(db=..., gpu=...) — no llm= is needed, because runtime.cohort_builder() only ever touches database(), never backend() (verified against runtime.py) — attaches the same file-handler logging as the interactive session (§3) to <plan folder>/log.txt, and calls CohortBuilder.build with an on_step callback that logs a line before each of the three phases (discovering the cohort, reading the profile matrix, assembling and writing the biom). It writes status.txt as RUNNING on start and DONE/FAILED on exit, and a final report.txt — the BuildReport's str() — next to the biom.

7.1 GPU mode: wiring in Anna's Sirius extension

Anna's benchmark (§ below) already has a working GPU pipeline on this cluster: a custom-built DuckDB extension at /private/pinto-lab/anna/sirius/build/sirius.duckdb_extension that adds gpu_buffer_init() and a gpu_processing($$ ... $$) table function. DuckDbConnection (adapters.py) gets one new constructor argument, gpu: bool = False:

class DuckDbConnection:
    def __init__(self, db_path, gpu=False):
        self._connection = duckdb.connect(str(db_path), read_only=True)
        self._attach_sources()
        self._gpu = gpu
        if gpu:
            self._connection.execute(f"LOAD '{SIRIUS_EXTENSION_PATH}'")
            self._connection.execute("SELECT gpu_buffer_init()")

    def query(self, sql, params=None):
        q = f"SELECT * FROM gpu_processing($$ {sql} $$)" if self._gpu else sql
        return self._connection.execute(q, params or []).fetch_df()

runtime.Settings gains a matching gpu: bool = False field, threaded through config(db=..., gpu=...) to database()'s DuckDbConnection(...) construction. Every query on that connection is wrapped uniformly when GPU mode is on — discovery, profile reads, metadata reads alike — rather than picking and choosing which queries "deserve" it; the interactive session's own connection is never GPU-mode, only a worker's is, so this never affects the fast attribute/preview queries a live session depends on. Fails fast, not silently: if gpu=True and the extension file is missing, the worker's LOAD raises immediately rather than quietly falling back to CPU — a GPU job that silently ran on CPU would look successful and cost 2 minutes to discover it wasn't.

/private/pinto-lab/anna/sirius/... is Anna's own home-directory build, not a tools-owned path. This is a known fragility, accepted for now: revisit if she moves or rebuilds it and the path stops resolving.

7.3 The watch view

One function, shared by "Watch progress" here and by reattaching via askslm load (§5.2): reads job.id, polls squeue -j <id> every few seconds, and tails log.txt underneath it, refreshing in place. Ctrl-C returns to the menu without touching the job — watching is read-only, closing the view never cancels anything. When status.txt flips to DONE or FAILED (or the job drops out of squeue entirely — finished jobs do), the view prints the final report.txt and returns to the menu on its own.

job 4213765 · RUNNING · queued 0:04:12
  [1/3] discovering cohort...        12.4s
  [2/3] reading profile matrix...    running (0:02:31)
Ctrl-C to stop watching (job keeps running)

8. Deliberate limits

  • No automatic retry. A FAILED job is surfaced as-is in the watch view and report.txt/log.txt; resubmitting means choosing Run it again. No backoff, no retry count to configure.
  • No poller/daemon. Status is read on demand (by the watch view or the next askslm load), never pushed. If a job is cancelled outside askslm entirely (a bare scancel from another session), status.txt just stays RUNNING until something reads squeue and notices it's gone — an acceptable gap, not a service worth building.
  • GPU mode has no fallback. Missing extension = hard failure, by design (§7.1) — never a silent CPU run that looks like a GPU run.
  • No log rotation or size cap. One question, one build, one log file — not a long-running service. Add a cap only if a real log is ever observed to be a problem.
  • plans/ is never garbage-collected automatically except via an explicit Discard (which now also scancels a live job first, §5.2). Old folders accumulate; that is the intended trail, not a leak.
  • askslm load never writes a second plan.json. Its fresh plans/<ts>/ folder exists only for log.txt, job.id/status.txt, and the default biom path — the plan itself lives at whatever path the caller passed in, and loading never copies or rewrites it.
