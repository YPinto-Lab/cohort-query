Session run-directory, logging & run UX accepted 2026-08-20

Every question gets a folder on disk; every run leaves a log; "Run it" stops looking like it hung.

2026-08-20 · touches only src/askslm/cli/session.py and src/askslm/build.py · no change to the public API surface

1. The problem this fixes

A real session on the server, right after picking sources and confirming output:

? What now? Run it
? Which feature space? STAT
? Which sources? (order = precedence) done
? What now? (Use arrow keys)

Nothing between "done" and the next menu tells you a multi-minute build ran, where it wrote, or whether it's safe to assume it finished. Separately: nothing survives a session except what you manually choose to Save plan and quit, and there is no record at all of what the LLM was actually sent or what SQL actually ran — the only way to find out is Show the SQL and overlap, and only for the current plan, only while the session is still open.

2. Plan folder: one per question

The instant _session() reads a question (first ask, "Refine the question", or "Ask new question"), before calling askslm.ask(), it creates:

plans/<YYYYMMDD_HHMMSS>/
  log.txt      # created immediately -- captures the run even if ask() throws
  plan.json    # written only if ask() returns with plan.error is None
  cohort.biom  # default "Run it" output target; still overridable

Every question is a new folder — refining keeps the text pre-filled but is still a new ask() call, so it gets a new timestamp. The previous folder is left on disk exactly as it was; nothing merges across refinements. No collision handling is added for two questions in the same second — that has never happened in practice and mkdir would just raise if it did.

3. Logging: what goes in log.txt

Stdlib logging, one file handler per plan folder, attached to the askslm logger when the folder is created and removed (not just replaced) when the next one is. Three call sites feed it:

  • cli/session.py — one logger.info(...) beside every questionary .ask(): which prompt, what was answered. This is the only new logging call site that is CLI-specific; it is what makes the whole session replayable from the log alone.
  • adapters.py, GeminiBackend — prompt text, raw response text, and elapsed time around translate, expand, and repair. These already exist as three separate methods on one class; logging wraps each, it does not change what they do.
  • adapters.py, DuckDbConnection.query — the SQL string, row count, and elapsed time. One hook, because every SQL execution in the system — attribute retrieval, cohort discovery, profile reads — already funnels through this one method on the Database port. No other file needs a logging call for SQL to be fully captured.
This is observability, not new behavior: nothing here changes a return value, a retry count, or an error path. CannedLlmBackend and any test double are untouched — logging lives in the concrete adapters, not the ports, so the fakes the test suite injects keep running with no log file and no handler at all.

4. Auto-save replaces manual save

Immediately after askslm.ask() returns, if plan.error is None, the session writes plan.json into that question's folder itself — the same Plan.save that "Save plan and quit" used to call explicitly. A translation failure or an error that survived the one repair attempt is not saved as a plan; log.txt is the only record of that attempt, which is the point of writing it before the outcome is known.

5. Menu

? What now?
 » Run it
   Refine the question
   Ask new question
   Show the SQL and overlap
   Discard
   Quit
ChoiceBehavior
Refine the question Re-opens the text prompt pre-filled with the current question text. New plan folder on submit, as above.
Ask new question Same, but the text prompt starts blank — for an unrelated cohort, not a wording tweak.
Discard Deletes the current plan folder (plan.json, log.txt, any cohort.biom already written) and drops straight into a blank "Ask new question" prompt — for a cohort that turned out to be junk.
Save plan and quit Removed. Redundant now that a successful plan is always already on disk.

6. Run progress

CohortBuilder.build (build.py) takes one new optional argument, on_step: Callable[[str], None] | None = None, called with a short label immediately before each of its three existing phases: discovering the cohort, reading the profile matrix, assembling and writing the biom. Nothing about the phases themselves changes — this is a callback inserted between three lines that already ran in this order.

_run in session.py prints the resolved output path before starting, then a line per step with elapsed time as each completes:

Building cohort -> plans/20260820_143012/cohort.biom
  [1/3] discovering cohort...        12.4s
  [2/3] reading profile matrix...    done
  [3/3] assembling + writing biom... done
Wrote plans/20260820_143012/cohort.biom (2.1 GB)

The default "Write to" answer in the source-picking prompt changes from feature_table.biom to <plan folder>/cohort.biom; typing a different path still overrides it.

7. Deliberate limits

  • Still synchronous. The terminal blocks for the whole build, same as today. A background/return-to-menu-immediately design was considered and explicitly rejected for this round — the progress lines are judged sufficient; revisit only if a build actually needs to run unattended.
  • No log rotation or size cap. One question, one short session, one log file — not a long-running service. Add a cap only if a real log is ever observed to be a problem.
  • plans/ is never garbage-collected automatically except via an explicit Discard. Old folders accumulate; that is the intended trail, not a leak.
