Concept embedding search proposed 2026-08-25

Retrieval that survives paraphrase: finding the field or value that means what the researcher meant, not just what they typed.

2026-08-25 · extends Docs/superpowers/specs/2026-08-19-attribute-retrieval-design.html, which named this exact gap and deferred it: "A synonym layer or embedding search is the obvious extension, and is deliberately not v1 — measure whether the simple thing fails first." We measured. It fails.

1. The question that found this

A real, saved plan (Workspaces/IBD_calprotectin/0_inputs/plan.json), run against the real mirror:

? What cohort do you need? IBD fecal metagenomic with calprotectin

The query returned 1,261 samples. It missed PRJNA1265906 / SRP586738 — a real cohort with fecal calprotectin measurements on every run — even though nothing about the question or the data was ambiguous to a human reading it. Verified against the real mirror:

  • Those runs pass every other filter: librarysource = 'METAGENOMIC', a human-gut biosamplemodel, and a populated fecalcalprotectin_run jattr value.
  • They fail only the IBD-detection clause, which checks sra_study/sample_name/attributes text for the literal strings "IBD" or "inflammatory bowel disease". This study's study ID and sample names (SRP586738, GB_513_1, …) contain neither.
  • The mirror already has the field that would have caught it — ibd_sam exists on 44,976 runs, alongside host_disease_sam (5.6M), disease_sam, ibd_diagnosis_sam, and others — but the translator never saw it.
Root cause, verified: attributes.py's _terms() drops any question word shorter than MIN_TERM = 5 characters before it is ever tried as a substring search term. "IBD" is 3 characters — discarded before the search against attribute_keys runs at all. The only other path into the search-term set is expansion.py's LLM call, whose instruction is written narrowly around measurement spelling variants ("calprotectin" → "calpro", "s100a8") and gives no guarantee of emitting the bare diagnosis acronym itself. Nothing put "ibd" back in.

The same failure mode exists one layer down, on values rather than keys. Metalog's subject_disease_status — a real, low-cardinality column, already fully shown by the catalog (201 distinct values, not truncated) — has no "IBD" value at all. It has "Crohn's disease" (1,682 rows) and "ulcerative colitis" (1,679 rows) as two separate literals. A question naming the umbrella term will never match either without knowing they're the same disease family.

2. Why lexical retrieval can't be patched further

The 2026-08-19 design deliberately shipped substring matching (plus one LLM call, expansion.py, to guess plausible field-name spellings) and flagged the ceiling: matching is lexical, not semantic. "IBD" and "Crohn's disease" share zero substrings — no length threshold tweak, no bigger MAX_KEYS budget, and no amount of prompt wording fixes a problem that is about meaning, not spelling.

Two ways to close a semantic gap were considered and rejected:

  • A hand-built concept → field/value table. Infeasible: 35,768 keys × arbitrary research questions (disease, assay type, geography, body site, …) is not something any person or group can anticipate and maintain.
  • Guess synonyms fresh on every question, via a bigger LLM prompt. Rejected once we established the mirror only rebuilds rarely (~yearly): the real vocabulary is static and already fully knowable at build time. Re-guessing a static, knowable answer on every single ask() call is waste, and it's non-deterministic waste — the same question could get different candidate fields on different runs.

3. The design: embed once at build, retrieve by similarity at query time

Same shape as the 2026-08-19 design — index once, search per question — with the index now semantic instead of purely lexical, and layered on top of the existing substring search rather than replacing it.

3.1 Build time (Scripts/build_mirror/, run when the mirror rebuilds)

  1. Embed every attribute_keys.key (~35,768 jattr field names) with Gemini's embedding model.
  2. Embed every value of every column schema_catalog already marks as low-cardinality / not truncated (e.g. subject_disease_status's 201 values, librarysource's 9) — reusing the existing truncation cutoff, no new threshold to invent.
  3. Store both as vector columns in new tables inside the same mirror file (e.g. attribute_key_embeddings(key, vector), column_value_embeddings(table_name, column_name, value, vector)), indexed with DuckDB's vss extension.

3.2 Query time (ask(), in the package)

  1. Embed the question's terms with one live Gemini API call — same pattern as the existing translation call, same free-tier budget class, no local model dependency.
  2. Nearest-neighbor lookup via vss against both embedding tables.
  3. Union the results into attributes.py's existing candidate set, alongside the substring-search hits from AttributeIndex / expansion.py — same per-term budget and ranking logic (MAX_KEYS, per-term slots) already documented there. Exact/near-exact matches are still free and instant; embeddings only do the work substring search can't.
"IBD fecal metagenomic with calprotectin"
   -> substring search: calprotectin -> calpro/s100a8 variants (as today)
   -> embedding search: "IBD" -> nearest neighbors in attribute_key_embeddings
      -> ibd_sam, host_disease_sam, disease_sam, ibd_diagnosis_sam (all real, all populous)
   -> embedding search: "IBD" -> nearest neighbors in column_value_embeddings
      -> subject_disease_status = "Crohn's disease" / "ulcerative colitis"
   -> union -> prompt gains the candidates it was missing, same shape as before
No new exclusion-guidance prompt rule (e.g. "shotgun must not match 16S") is being added. Once retrieval surfaces the real enumerated values, the model reads them directly off the catalog the same way it already does today — that guardrail would be solving a problem better retrieval already solves.

4. Verified mechanics

Everything below was checked against the real mirror and lab server before this design was written.

QuestionAnswer
Does attribute_keys already have the fields this needs? Yes — ibd_sam (44,976 runs), host_disease_sam (5.6M), disease_sam, study_disease_sam, ibd_diagnosis_sam, ibd_diagnosis_refined_sam, and more, all already indexed by the 2026-08-19 design. The gap is retrieval, not data.
Does subject_disease_status contain an "IBD" literal? No. 201 distinct values; disease is split into "Crohn's disease" (1,682) and "ulcerative colitis" (1,679) with no umbrella term.
Is a value census feasible for SRA's free-text ID columns (sample_name, sra_study)? No. 30.5M distinct sample_name values across 39.1M rows — these are identifiers, not vocabulary. Only schema_catalog's already-low-cardinality columns are in scope for value embedding.
Does DuckDB's vss extension load on the lab server? Yes — installs and loads cleanly against the real mirror's DuckDB version.
Does the lab server have internet access for the embedding API? Yes — reaches generativelanguage.googleapis.com.
Is a new heavy dependency (e.g. torch for a local embedding model) needed? No. google-genai is already a package dependency and already installed; no sentence-transformers/torch present or required.
Does embedding cost money? No — Gemini's embedding model is free-tier (10M tokens/minute), a separate quota pool from the translation model. The one-time build-time embedding of ~36K terms and the per-question query-time calls both stay well inside free-tier headroom.
Which embedding model? Currently gemini-embedding-001 (text-embedding-004 was deprecated January 2026). Google deprecates these on a roughly annual cadence — confirm the current recommended model at implementation time rather than trusting this table.

5. Deliberate limits

  • jattr key values are not embedded — only key names, and only the values of real low-cardinality columns. A per-key value census (e.g. distinct values of host_disease_sam itself) would need new per-key cardinality computation at ETL time; it's not in this design. Mirrors the existing asymmetry from 2026-08-19: keys are indexed, their values are not.
  • No client-side embedding cache. Each ask() makes one live embedding call, same pattern as the existing translation call. Free-tier headroom and latency don't justify a cache with invalidation concerns.
  • No sidecar vector index. Vectors live inside the same mirror file via vss — one file, one source of truth, package still never builds or writes it.
  • Retrieval only, not translation. The final SQL predicate is still a literal, reviewable =/ILIKE/IS NOT NULL written by the one existing translation LLM call. Embeddings only change which candidates get shown to it — the Plan stays a reviewable, replayable SQL artifact.

6. Eval

Two new cases in Scripts/eval/questions.jsonl, gold SQL verified executable against the real mirror (real row counts, not guessed), marked as unreviewed by the domain owner per the file's existing convention:

  • An IBD question worded without the literal word "IBD" — the PRJNA1265906-shaped case above.
  • A shotgun/mgx question that must resolve to librarysource = 'METAGENOMIC' and must not match AMPLICON rows.

run_eval.py runs before and after the change, against the real backend, to confirm no regression on the existing three cases and that both new cases pass.
